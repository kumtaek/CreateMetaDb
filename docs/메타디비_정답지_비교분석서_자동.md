## 개요
- 대상 프로젝트: SampleSrc
- 비교 기준: 수작업 정답지(소스 전수 분석) vs 실제 메타DB 집계(report_metrics.json)

## 세부 분석 및 원인 추정
- CALL_QUERY(53) 부족
  - mapper_map 미사용(스킵) 환경에서 METHOD→SQL 매칭이 이름 기반 폴백에 의존
  - 일부 SQL_* component_name이 namespace.id 규약으로 생성되지 않은 케이스 가능
  - Java/JPA 경로의 쿼리 호출이 CALL_QUERY로 일원화되지 않은 부분 존재 가능

- USE_COLUMN(0) 누락
  - SQL 저장 직후 컬럼 사용 관계 생성 경로가 호출되지 않거나, CommonSqlAnalyzer 결과 반영 누락 가능
  - 즉시 반영 로직(java_loading/xml_loading)과 배치 분석(CommonSqlAnalyzer)의 USE_COLUMN 저장이 비활성/미호출 상태일 수 있음

- JOIN_MERGE(0)
  - 데이터셋 특성상 MERGE가 SELECT 래핑으로 들어가 JOIN 추출이 어려운 패턴 존재
  - parser/sql_parser의 MERGE … USING … ON 추출은 구현됨. 관계 저장 연결 확인 필요

## 개선 권고안(실행 우선순위)
1) CALL_QUERY 증대
   - SQL_* component_name = "namespace.id" 강제 생성 여부 재확인 (모든 매퍼 경로에 적용)
   - RelationshipBuilder의 이름 기반 폴백 확장: class tail(Impl/Repository/Dao/Mapper) 우선순위 강화, project_id 스코프 매칭 엄격화
   - JPA/직접 SQL 호출 경로에서 CALL_QUERY 보강(필요 시 별도 패턴 추가)

2) USE_COLUMN 생성
   - java_loading/xml_loading에서 SQL 저장 직후 USE_COLUMN 생성 경로 강제 호출
   - CommonSqlAnalyzer.analyze_all_queries() 결과로 USE_COLUMN 저장 보강 및 멱등화(INSERT OR IGNORE)

3) MERGE 계열 JOIN 확인
   - MERGE USING … ON 패턴의 JOIN_MERGE 저장 경로 연결(분석 결과 → relationships 반영) 재검증

## 결론
- 전체적으로 API_URL→METHOD, SQL→TABLE, JOIN 합계는 정답지 기준선에 부합
- METHOD→SQL(CALL_QUERY), USE_COLUMN은 추가 보강 필요(누락)
- 권고안 적용 후 재실행/재검증을 권장하며, 반영 완료 시 본 비교서를 갱신합니다.
