# 개발 완료 내역 (최종)

본 문서는 소스 분석기 개선 작업의 최종 개발 내역을 정리합니다. 모든 변경은 UTF-8(무BOM), 4 space 인덴트, 경로키(file_path + file_name) 일관성을 준수하도록 적용했습니다.

## 1. SQL 1패스 파서 전면 개선
- 파일: `parser/sql_parser.py`
- 목적: 저장 즉시 관계 생성과 후속 리포트 정합성을 위해 SQL을 1패스로 안전하게 분석
- 주요 기능
  - 전처리: MyBatis 동적 태그 제거, 주석 제거, 공백/바인딩변수 정규화
  - 테이블/별칭 추출: FROM/UPDATE/DELETE/INSERT/MERGE/USING/JOIN에서 테이블 식별 및 별칭 매핑
  - 컬럼 추출: SELECT/WHERE/ON 구간의 `ALIAS.COLUMN` 토큰 추출
  - 조인 분석: 
    - 명시적 JOIN: `INNER/LEFT/RIGHT/FULL JOIN ... ON a.col=b.col`
    - 암시적 JOIN: `WHERE a.col=b.col` 및 Oracle `(+)` 패턴
    - MERGE JOIN: `MERGE ... USING ... ON (a.col=b.col)`
- 기대효과
  - 저장 직후 USE_TABLE/JOIN/USE_COLUMN 관계를 안정적으로 생성
  - 후속 배치 분석(CommonSqlAnalyzer)와 수치 정합성 향상

### [수정 사유]
- 기존 파일에 비가시 제어문자/깨진 도큐스트링이 혼재하여 import 단계에서 간헐적 SyntaxError 유발(특히 XML 단계 진입 시 실패). 이로 인해 전체 파이프라인 수행과 리포트 생성이 중단됨.
- 기존 파서의 테이블/조인/컬럼 추출이 다단계·분산되어 있어 “저장 즉시” 관계 생성이 불안정했음. MERGE … USING … ON 패턴과 WHERE 기반 암시적 조인, SELECT/WHERE/ON 컬럼 추출 사이에 정합성 갭이 발생.
- MyBatis 동적 태그(<if/choose/when/where/set/trim/foreach>) 및 바인딩 변수 치환(#{}, ${}) 전처리가 일관되지 않아 케이스별 편차가 있었음.

### [개선 내용 요약]
- UTF-8(무BOM)로 클린 재작성하여 인코딩/문자열 문제 제거.
- 전처리 통합: 동적 태그 제거 → 주석 제거 → 공백 정규화 → 바인딩 변수 정규화 → 대문자 변환.
- 1패스 분석 강화: FROM/JOIN/USING/MERGE에서 테이블/별칭, SELECT/WHERE/ON에서 컬럼, MERGE ON/명시적/암시적 조인 모두 식별.

### [개발 내역(상세)]
- 파일: `parser/sql_parser.py`
  - API
    - `extract_table_names(sql) -> Set[str]`: FROM/JOIN/USING/MERGE 패턴에서 테이블 후보 수집 후 키워드/형식 검증
    - `extract_tables_and_aliases(sql) -> Dict[str,str]`: 테이블→별칭 역매핑(alias→table) 구성(USING/JOIN 포함)
    - `extract_columns(sql) -> List[str]`: SELECT/WHERE/ON 구간에서 `ALIAS.COLUMN` 토큰 수집(대소문자 무시)
    - `analyze_join_relationships(sql) -> List[Dict]`: 명시/암시/MERGE 조인 리스트 통합 반환
  - 전처리
    - MyBatis 태그 제거(`<if/choose/when/otherwise/where/set/trim/foreach>`)
    - 주석 제거(`--`, `/* */`), 공백 정규화, 바인딩 변수 정규화(`#{}`, `${}` → `?`)
  - 정규식 안전장치
    - `re.DOTALL|IGNORECASE` 사용, Oracle 키워드 블랙리스트로 오탐 감소
  - 스키마 접두사 처리
    - `OWNER.TABLE` 형식은 `TABLE`로 정규화(`split('.')[-1]`)
  - 케이스 민감도
    - 내부 처리는 대문자 변환, 상위 모듈 표현은 원문 유지(경계 구분)

### [검증 항목]
- 저장 직후 관계(USE_TABLE/JOIN/USE_COLUMN) 유무와 배치 분석 결과 비교
- MERGE/USING/암시적 조인 포함 케이스에서 테이블/별칭/컬럼 매칭 정확성 확인

### [효과/영향]
- 저장 직후 USE_TABLE/JOIN/USE_COLUMN 생성의 신뢰도 상승(자바/마이바티스 경로 모두).
- XML/Java 단계에서 SyntaxError 제거로 메인 파이프라인 안정화 및 리포트 생성 정상화.
- RelationshipBuilder, CommonSqlAnalyzer와의 결과 정합성 개선(중복/누락 감소).

### [검증/리스크 완화]
- sampleSrc 대상으로 전체 파이프라인 실행(강제 재생성) 통해 XML→Java→API→관계 빌드까지 연속 실행 확인.
- 정규표현식 기반 추출은 방어적으로 설계하고, Oracle 키워드 필터 적용으로 오탐 완화.
- 과도한 정규화의 부작용(케이스 유지 필요 지점)은 상위 모듈에서 원본문 사용을 유지하도록 경계 구분.

## 2. RelationshipBuilder 정밀 휴리스틱 통합
- 파일: `relationship_builder.py`
- 변경 사항
  - API_URL → METHOD 폴백은 “HTTP:methodName” 패턴만 허용 (예: `GET:selectUser`).
  - `'/api/...:GET'` 같은 URL:HTTP 형식은 폴백에서 제외 → 오탐 감소.
  - Controller 클래스 선호 정렬 유지.
  - 관계 저장은 `INSERT OR IGNORE`(멱등) 준수.

## 3. SQL 저장 시 즉시 관계 생성(보완 저장)
- 파일: `java_loading.py:145`
- 내용: `SqlContentManager.save_sql_content` 성공 직후,
  - SQL 주석 제거/별칭 추출 → JOIN(명시/암시/MERGE) 저장
  - 컬럼 사용 추출 → `SQL(component) -> COLUMN(component)` USE_COLUMN 저장
- 효과: CommonSqlAnalyzer 실행 전에도 즉시 ERD/시퀀스 정합성 확보.
- 비고: MyBatis XML 경로(`xml_loading.py`)에도 동일 로직 적용 준비 완료. 파일 내 인코딩 특성(특수문자)로 패치 매칭이 민감하여, 안정성 확보 후 동일 보완 로직을 삽입할 예정입니다.

### [수정 사유]
- 저장 직후 USE_TABLE/JOIN/USE_COLUMN이 없으면, 분석 중간 산출물(리포트/뷰어)에 공백이 생기고, 후속 배치 분석까지 지연됨.
- 메소드별 다건 SQL 케이스에서 즉시 반영이 없으면 체인(메소드→쿼리→테이블) 파악이 늦어짐.

### [개선/효과]
- 저장과 동시에 관계를 생성하여 체인 가시성 즉시 확보.
- 배치 분석(CommonSqlAnalyzer)은 보강 역할로만 수행되어 중복/경합 최소화.

### [개발 내역(상세)]
- 적용 위치 및 흐름
  - 파일: `java_loading.py:145` (`_process_collected_queries` 내부)
  - 단계:
    1) `SqlContentManager.save_sql_content(...)` 호출로 SQL 컴포넌트 및 SqlContent.db 저장
    2) 저장 성공 시, 즉시 보완 분석 수행
       - 전처리: 주석 제거(`CommonSqlAnalyzer._remove_comments`), 공백 정규화는 Analyzer 내부 로직 사용
       - 테이블/별칭 추출(`_extract_tables`) → alias_map 확보
       - 조인 추출: 명시적 JOIN(`_extract_explicit_joins`), 암시적 JOIN(`_extract_implicit_joins`), MERGE ON(`_extract_merge_joins`)
       - 컬럼 추출: SELECT/WHERE/ON 구간의 `ALIAS.COLUMN`(`_extract_columns`)
    3) 저장 로직
       - JOIN: TABLE(component) 간 `JOIN_*`를 `relationships`에 저장(`_save_table_joins_components`)
       - 컬럼: 방금 저장된 SQL component_id를 조회한 뒤 `USE_COLUMN` 저장(`_save_use_column_relationships`)
  - XML 경로도 동일 패턴으로 적용 예정(`xml_loading.py` 저장 성공 분기 직후)

- 데이터/DB 포인트
  - `components`의 SQL_* 컴포넌트 식별: 방금 저장한 `component_name`으로 역조회(프로젝트 스코프 제한 + 최신건 우선)
  - `relationships` 저장은 멱등을 목표로 `INSERT OR IGNORE`(내부 util 사용) 또는 중복 체크 후 삽입
  - `files` 테이블 키: `file_path` + `file_name`(경로키 일관성) 유지, 모든 조회는 해당 조합으로 수행

- 설계 고려사항
  - 성능: 저장 직후 수행하되, 단일 파일 기준 상수 시간 내 처리(정규표현식 기반)
  - 신뢰도: Oracle 키워드 필터로 오탐 완화, 별칭 맵을 활용해 `MERGE/USING/ON` 케이스도 커버
  - 일관성: 저장 즉시 생성된 관계는 배치 분석 결과와 충돌하지 않도록 동일 기준의 파서/분석기를 사용
  - 실패 허용: 보완 분석 실패는 전체 저장을 방해하지 않으며(try/except), 로깅 후 계속 진행

- 엣지 케이스 및 대응
  - 혼합 대소문자/줄바꿈/주석 내 키워드 → 전처리 및 `re.DOTALL/IGNORECASE`로 처리
  - 다중 쿼리/동일 id 충돌 → `component_name` 기반 최신 저장건 우선, UPSERT 정책 유지
  - 스키마 접두사(OWNER.TABLE) → `split('.')[-1]`로 테이블명 정규화, Oracle 키워드 제외

- 검증 방법
  - sampleSrc로 전체 파이프라인 실행 후, 저장 직후에도 ERD/시퀀스에서 USE_TABLE/JOIN/USE_COLUMN이 보이는지 확인
  - 배치 분석 전/후 관계 수치 비교, 중복 생성(멱등성) 여부 확인

## 4. 경로키(file_path + file_name) 일관성 준수
- 모든 로더/유틸에서 DB 조회 시 `files.file_path` + `files.file_name` 조합 사용
- 전체 경로 재구성 시: 프로젝트 루트 + `file_path` + `file_name` + `PathUtils` 정규화(`/`) 사용
- 영향: 파일 식별/중복/관계 매핑의 일관성 보장
 
### [수정 사유]
- Windows/Unix 경로 구분자 혼재로 인한 `file_path` 불일치가 발생하면 동일 파일이 서로 다른 키로 인식되는 문제가 있었음.
- `'.'`/빈 디렉터리의 표현이 혼용되면 루트 파일 조회가 실패할 수 있음.
 
### [개발 내역(상세)]
- 파일: `java_loading.py`
  - `_get_file_id(...)`에서 경로 계산 방식을 `PathUtils().normalize_path_separator(..., 'unix')`로 통일
  - `file_dir in ('', '.')`이면 `''`로 정규화하여 DB키 일관성 확보
- 파일: `xml_loading.py`, `util/mapper_indexer.py`
  - 기존에도 `PathUtils` 기반 정규화로 동작. 점검 시 문제 없음.
 
### [검증]
- `files` 테이블 키가 `file_path + file_name` 조합으로 조회되는지 각 로더에서 확인
- 경로에 역슬래시가 포함된 입력에서도 동일 파일이 중복 키로 생성되지 않는지 재실행 검증

## 5. Controller/Mapper 인덱싱 보완 저장
- Controller: `backend_entry_loading.py`
  - `controller_api_map` UPSERT 유지, API identity 해시 사용
  - 저장 직후 RelationshipBuilder가 정밀 소스 우선으로 CALL_METHOD 생성
- Mapper: `util/mapper_indexer.py`
  - MyBatis `namespace + id` 인덱싱 → `mapper_map` UPSERT
  - RelationshipBuilder가 `mapper_map` 우선으로 METHOD→SQL(CALL_QUERY) 생성(엄격/유연 매칭 혼합)

### [수정 사유]
- Controller 측 API 연결 정보와 Mapper의 `namespace.id` 매핑은 정밀한 1차 소스입니다. 이를 우선 활용하지 않으면 폴백(문자열 매칭)으로 인해 오탐/누락이 발생할 수 있습니다.
- 재분석/증분 시 중복 생성이 발생하지 않도록 멱등 저장(UPSERT/INSERT OR IGNORE)이 필요합니다.

### [개발 내역(상세)]
- Controller 인덱싱
  - 파일: `backend_entry_loading.py`
  - 처리: 백엔드 엔트리 분석 시 `build_api_identity_key(url, method)`로 identity 생성 → `controller_api_map` UPSERT
  - 활용: RelationshipBuilder가 `controller_api_map` 조인으로 API_URL→METHOD(CALL_METHOD) 생성
  - DB 포인트: `identity_hash`로 일관된 키 유지, `file_id`/`class_name`/`method_name`/`http_method`/`url` 저장

- Mapper 인덱싱
  - 파일: `util/mapper_indexer.py`
  - 처리: 프로젝트 소스의 MyBatis XML을 순회 → `<mapper namespace>`와 쿼리 `id` 추출 → 같은 XML에서 수집된 SQL_* 컴포넌트(component_name==id) 역매칭 → `mapper_map` UPSERT
  - 활용: RelationshipBuilder가 `mapper_map` 기반으로 METHOD→SQL(CALL_QUERY) 생성
    - 엄격 매칭(클래스명==네임스페이스 말단, 메소드명==id) 우선
    - 유연 매칭(클래스명이 말단으로 끝나는 경우 e.g., `UserMapperImpl`)을 보조로 허용
  - DB 포인트: `project_id/file_id/namespace/query_id/sql_component_id/del_yn` 저장, 멱등 UPSERT

### [효과/영향]
- 정확한 1차 소스(controller_api_map/mapper_map)를 우선 사용하여 폴백 의존도를 낮춤 → 오탐/누락 감소
- 재실행/증분에도 관계 중복 최소화(UPSERT/IGNORE)
## 6. 전체 실행/리포트
- 실행: `python main.py --project-name sampleSrc --force`
- 리포트: `python create_report.py --project-name sampleSrc`
- 검증 포인트
  - API_URL→METHOD, METHOD→SQL, SQL→TABLE(USE_TABLE) 카운트 확인
  - JOIN_* 및 USE_COLUMN 증가 확인 (즉시 반영 + 배치분석 융합)

### [유의사항]
- Windows 콘솔 cp949 인코딩으로 한글 에러 메시지 출력 시 `UnicodeEncodeError`가 발생할 수 있으나 기능 영향은 없음(로그 파일은 UTF-8 기준).


## 7. 남은 보완 (예정)
- `xml_loading.py` 저장 직후 즉시 JOIN/컬럼 관계 생성 코드 삽입(자바 경로와 동일). 
  - 파일 내 특정 문자열 인코딩 문제로 안전 매칭 처리가 필요하여, 사전 정규화 후 반영 예정.
- 로그 인코딩(cp949) 때문에 한글 에러 메시지 출력 시 `UnicodeEncodeError`가 발생할 수 있음. 기능 영향은 없으며, 추후 로거 스트림 인코딩 옵션으로 완화 가능.

## 부록: 기준 및 가이드
- 코딩 스타일: Python 3.11+, 4 space, UTF-8(무BOM)
- API 이름/해시: `util/api_naming.py` 사용 (프론트/백 통합, `GET:method` 형태)
- 관계 생성 우선순위: `controller_api_map`, `mapper_map` → 폴백(안전)
- 관계 저장: `INSERT OR IGNORE` 멱등 권장
### [수정 사유]
- 기존 폴백이 `'/api/users:GET'` 같이 “URL:HTTP” 형식까지 메소드명으로 오인 매칭하여 오탐(CALL_METHOD)이 발생.
- Front/Back 통합 명명 규약(API_NAMING: `HTTP:method`)을 준수하지 않는 값을 폴백 소스로 쓰면, controller_api_map의 정밀 매핑을 침해하고 그래프 품질을 떨어뜨림.
- 폴백은 “정밀 소스 부재 시, 최소한의 안전 장치”로 동작해야 하므로 범위를 좁히고, 우선순위(Controller 계층)를 명확히 해야 함.

### [개발 내역(상세)]
- 파일/라인: `relationship_builder.py:186`
- 로직 요약
  - API_URL 컴포넌트명 파싱 시 `':'` 포함 여부 확인 → 좌측 토큰이 HTTP 동사 집합 `{GET, POST, PUT, DELETE, PATCH, OPTIONS}`에 포함되는 경우에만 유효로 간주.
  - 우측 토큰을 메소드 식별자 후보로 사용하되, 슬래시(`/`) 포함 또는 전체 대문자(상수/URL 흔적)일 경우 제외.
  - 후보 메소드명으로 METHOD를 조회할 때, `LEFT JOIN classes cl`을 이용하여 클래스명이 `Controller`를 포함하는 항목을 우선 정렬.
  - 관계 저장은 `INSERT OR IGNORE`로 멱등 보장(중복 방지).
- 선행 순서
  1) controller_api_map 기반 정밀 매핑
  2) mapper_map 기반 METHOD→SQL 매핑
  3) Front API 휴리스틱(이번 보강) — 최하위 우선순위

### [허용/차단 패턴 예시]
- 허용(매핑 시도): `GET:selectUser`, `POST:updateOrder`, `DELETE:removeItem`, `PATCH:applyCoupon`
- 차단(매핑 시도 안함): `/api/users:GET`(URL:HTTP), `GET:/api/users`(HTTP:URL), `GET:LIST_ALL`(상수성 대문자), `:method`(좌측 공란)

### [개선/효과]
- “HTTP:methodName”만 허용하여 폴백 오탐 급감 → controller_api_map의 결과가 우선 보존됨.
- Controller 클래스 선호 정렬로 실매칭 확률 상승.
- 관계 INSERT OR IGNORE로 재실행/증분 시에도 중복 생성 방지.
