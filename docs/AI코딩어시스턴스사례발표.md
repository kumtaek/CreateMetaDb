## 1. 발표 개요

### 발표 목적
본 발표는 **Java/Spring/MyBatis 기반 웹 애플리케이션 소스코드 분석 시스템** 개발 과정에서 AI 코딩 어시스턴스(ChatGPT, Claude Code, Gemini 등)를 활용하면서 겪은 **실패와 성공 경험**을 공유하고, AI 도구를 효과적으로 활용하기 위한 **실무 노하우**를 전달하고자 합니다.

### 핵심 메시지
> **"AI는 만능이 아니다. 업무와 IT를 겸비한 전문가만이 AI를 제대로 활용할 수 있다."**

## 2. 프로젝트 소개

### SourceAnalyzer란?
**프론트엔드 → 백엔드 → 데이터베이스**까지의 완전한 연관관계를 도출하는 메타데이터 분석 시스템입니다.

```
[JSP/Vue/React] → [Controller] → [Service] → [Mapper XML] → [SQL] → [Table/Column]
```

### 분석 대상 기술 스택
- **백엔드**: Java 클래스/메서드, Spring Framework, MyBatis XML, JPA
- **프론트엔드**: JSP, Vue, React, TypeScript, JavaScript
- **SQL**: Oracle EXPLICIT/IMPLICIT JOIN 분석, 테이블/컬럼 추출

### 7단계 분석 파이프라인
| 단계 | 역할 |
|------|------|
| 1단계 | 프로젝트 파일 스캔 |
| 2단계 | DB 스키마 로드 |
| 3단계 | MyBatis XML 파싱 |
| 4단계 | Java 클래스/메서드 추출 |
| 5단계 | Spring API 진입점 분석 |
| 6단계 | 프론트엔드 API 호출 분석 |
| 7단계 | 데이터 무결성 검증 |

## 3. 시행착오의 여정

### 3.1. 첫 번째 시도: 무계획 개발 요청 ❌

#### 상황
처음에는 단순하게 생각했습니다. "AI가 다 해주겠지"라는 막연한 기대로 LLM에게 **"소스분석기 개발해줘"**라고 요청했습니다.

#### 결과
AI는 거침없이 코드를 작성하기 시작했고, 겉보기에는 그럴듯해 보였습니다. 하지만 실제로 실행해보니 **의도와 전혀 다른 결과물**이 나왔습니다. 기대했던 연관관계 분석은 전혀 이루어지지 않았습니다.

#### 교훈
> **명확한 요구사항 없이 AI에게 개발을 맡기면 실패한다.**

---

### 3.2. 두 번째 시도: PRD 작성 후 개발 요청 ❌

#### 상황
"문서화부터 해보자"는 생각으로 **PRD(Product Requirements Document)**를 작성해달라고 요청했습니다. AI가 작성한 PRD를 기반으로 다시 개발을 요청했습니다.

#### 결과
이전보다는 나아 보였지만, 여전히 **완성된 시스템은 나오지 않았습니다**. PRD도 AI가 작성했기 때문에 실제 업무 맥락과 핵심 요구사항이 누락되었습니다.

#### 교훈
> **PRD 자체도 업무 전문가가 직접 작성해야 한다. AI는 형식만 갖춘 문서를 만들 뿐이다.**

---

### 3.3. 세 번째 시도: 파서 개발 요청 ❌

#### 상황
"Java 파서 개발해줘", "SQL 쿼리 파서 개발해줘"라고 세부 기능별로 요청했습니다.

#### 결과
AI는 **완벽한 문법 검증을 위한 정교한 파서**를 개발하려고 시도했습니다. 하지만 복잡도가 급격히 높아지면서 결국 **완성을 못하고 중단**되었습니다.

#### 문제의 본질
소스분석기의 목적은 **정확한 신택스 체크가 아닙니다**. 소스 간 연관관계를 분석하는 것이 목표입니다. 이 **개발 목표를 AI에게 정확히 인식시키지 못한 것**이 문제였습니다.

#### 교훈
> **AI는 방향 제시를 스스로 하지 못한다. "무엇을 위해" 개발하는지 명확한 목표를 사람이 알려줘야 한다.**

만약 정확한 파서를 개발해서 소스를 완벽하게 분석하는 것에 집중했다면, 복잡도가 너무 높아 **절대 완성하지 못했을 것**입니다.

---

### 3.4. 네 번째 시도: 메타DB 직접 설계 + PRD 보강 ❌

#### 상황
이번에는 **메타DB 스키마를 직접 설계**하고, PRD도 더 신경 써서 작성한 후 개발을 요청했습니다.

#### 결과
초기에는 진척이 있었습니다. 하지만 개발이 진행되면서 **복잡도가 높아지자 이전에 개발했던 소스를 망가뜨리기 시작**했습니다. 하나의 기능을 추가하면 기존 기능이 깨지는 현상이 반복되었습니다.

#### 교훈
> **AI는 전체 시스템의 맥락을 유지하지 못한다. 복잡도가 높아지면 이전 작업물을 "잊어버린다".**

---

### 3.5. 다섯 번째 시도: 설계 불변 원칙 강조 ❌

#### 상황
메타DB 설계 변경을 **절대 하지 말라**고 지침에 강조했습니다. 정규화를 지키고 조인을 통해 데이터를 조회하도록 설계했습니다.

#### 결과
그런데도 AI는 **몰래 스키마를 변경**했습니다. 조인해야 하는 데이터를 가져오기 위해 **자기 맘대로 컬럼을 추가**한 것입니다.

#### 상상 코딩의 문제
문서화를 해놔도, AI는 어디선가 학습한 **자신만의 관점으로 "상상 코딩"**을 합니다. 결국 DB 설계도, 소스도 엉망이 되었습니다. 복잡도가 높아지면 **어디서 뭐가 망가진 건지 찾기도 힘듭니다**.

#### 교훈
> **Git에 커밋해서 버전관리를 하지 않으면 복구 불가능하다. AI 작업 결과는 반드시 버전 관리해야 한다.**

---

### 3.6. 여섯 번째 시도: 검토 요청 → 바로 개발 시작 ❌

#### 상황
"XXX 검토해줘"라고 요청했습니다.

#### 결과
검토를 먼저 하는 것이 아니라 **바로 개발을 시작**해버렸습니다. 결과적으로 소스가 또 망가졌습니다.

#### 교훈
> **"검토해줘"라고 해도 AI는 개발을 시작한다. "개발하지 말고 검토만 해줘. 결과를 문서로 정리해줘."라고 명확히 지시해야 한다.**

---

### 3.7. 일곱 번째 시도: 분할 정복 전략 ❌

#### 상황
**Divide and Conquer** 전략을 적용했습니다. 분할 설계, 분할 개발, 단위 테스트를 진행했습니다.

#### 결과
각각의 모듈은 개발되었지만, **전체 기능을 통합하는 데 실패**했습니다. AI는 그저 **확률적으로 그럴듯한 소스 조각**을 개발할 뿐, 전체 로직을 이해하고 **퍼즐의 완전체를 맞추지 못합니다**.

#### 교훈
> **AI는 부분 최적화는 잘하지만, 전체 최적화는 사람이 해야 한다.**

---

### 3.8. 여덟 번째 시도: 중복 코드 문제 ❌

#### 상황
"중복 소스 개발 금지, 공통화 개발"을 지침으로 강조했습니다.

#### 결과
AI는 **기존에 개발된 소스가 있음에도 계속 중복된 기능을 개발**했습니다. 디버깅 시에도 중복된 소스의 일부만 수정하여 동작이 일관되지 않았습니다.

#### 건초더미에서 바늘 찾기 문제
규모가 커지고 복잡도가 높아지면 **전체를 보지 못하기 때문에** 중복 자체를 인식하지 못합니다. 이는 AI의 컨텍스트 윈도우 한계와 관련이 있습니다.

#### 교훈
> **코드 규모가 커지면 AI는 전체를 파악하지 못한다. 중복 방지는 사람이 관리해야 한다.**

---

### 3.9. 아홉 번째 시도: 정답지 기반 검증 ❌

#### 상황
메타DB가 올바로 생성되었는지 검증하기 위해 **정답지를 만들어 비교**하라고 했습니다. 차이가 있으면 개선하라고 지시했습니다.

#### 결과
AI는 근본적인 원인을 분석하고 개선하는 대신 두 가지 **야매 방법**을 사용했습니다.
1. **하드코딩 땜빵**: 특정 케이스만 맞도록 하드코딩
2. **정답지 수정**: 차이가 없도록 정답지 자체를 수정

#### 교훈
> **AI는 "차이를 없애라"는 목표만 달성하려 한다. 근본 원인 해결보다 우회 전략을 선호한다.**

## 4. AI와 협업할 때 필요한 것들

### 4.1. 명확한 목표 설정
- 개발의 **목적과 방향**을 분명히 제시
- "무엇이 아니라 왜"를 설명
- 예: "정확한 파서가 아닌, 연관관계 추적이 목표"

### 4.2. 설계의 불변 영역 지정
- **DDL 스키마 변경 금지** 등 변경 불가 영역 명시
- 파일에 읽기 전용(Read-Only) 속성 적용
- 변경 시도 시 에러 발생하도록 방어 코드 추가

### 4.3. 단계별 검증 프로세스
```
설계 → 검토 요청(문서화) → 수정 → 개발 → 테스트 → 커밋
```
- 각 단계에서 **검토 결과를 문서로 출력**하도록 요청
- "개발하지 말고 검토만"이라고 명시

### 4.4. 버전 관리 필수
- 모든 작업 단계마다 **Git 커밋**
- AI가 소스를 망가뜨려도 이전 버전으로 복구 가능
- 커밋 메시지에 작업 내용 상세 기록

### 4.5. 컴파일/테스트 자동화
- 개발 완료 후 **반드시 신택스 체크**
- 자동화된 테스트로 회귀 방지
- CI/CD 파이프라인에 검증 단계 포함

## 5. 모델 간 협업 및 토큰 관리 노하우

### 5.1. 유료 모델의 사용량 제한
Claude Code, Gemini Pro 등 유료 모델은 **사용량 제한**이 있습니다.
- Claude Code: 5시간 제한
- 토큰 사용량에 따른 비용 증가

### 5.2. 모델 간 핑퐁 전략

#### 설계 검토 핑퐁
```
Gemini Pro에게 설계 시켜 문서화
    ↓
Claude Code에게 설계문서 검토 요청
    ↓
Gemini에게 검토결과 재검토 요청
    ↓
... 반복
```

서로 다른 모델이 상호 검토함으로써 **편향을 줄이고 품질을 높일 수 있습니다**.

#### 질의서 기반 협업
모듈화 개발 중 전체 퍼즐을 맞춰야 할 때, 복잡도 증가로 해결하지 못하고 미궁에 빠지는 경우가 있습니다.

**해결 방법**:
1. AI에게 "너보다 똑똑한 시니어 개발자에게 질의서를 작성하라"고 요청
2. 다른 모델에게 질의서에 대한 **답변 문서 작성** 요청
3. 답변을 기반으로 원래 모델이 문제 해결

## 6. AI 코딩 어시스턴스의 한계와 가치

### 6.1. 현업의 오해 사례

#### 이미지 위변조 감지 기능 요청 사례
최근 현업 파트장이 ChatGPT에게 이미지 위변조 감지 기능 개발을 요청했습니다. "ChatGPT가 다 개발해줬으니 IT개발팀에서 적용만 해달라"고 요청이 왔습니다.

**실제 결과**:
- 위변조 인식 기능의 **알맹이(핵심 알고리즘)는 없음**
- 알맹이 함수가 개발되어 있다는 **가정 하에** 병렬 실행하는 껍데기만 존재

#### 바이브 코딩의 함정
유튜브에서는 "IT 비전공자도 AI로 코딩할 수 있다"고 합니다. 하지만 현실은 다릅니다.

> **IT도 알고, 업무도 알아야 AI에게 일을 제대로 시킬 수 있다.**

### 6.2. 빅테크의 교훈 - AI 부메랑

#### 미국 빅테크 기업 해고 후 조용한 재고용
빅테크 기업들이 AI 도입으로 개발자를 해고했지만, **조용히 재고용**하고 있습니다.

**이유**:
- AI가 소스를 엉망으로 만들어 놓음
- 검수하고 수정할 **사람이 없어서** 문제 발생
- 결국 사람이 필요함을 깨달음

### 6.3. 내부망 소규모 모델의 한계

#### 현황
- 내부망에 7B 모델로 코딩 어시스턴스 도입 검토 중
- 우리은행 등 금융권도 수십B 규모 SLLM으로 구현

#### 현실적 기대 수준
- 외부 SOTA 모델로도 만족스럽지 못한데, 내부망 소규모 모델은 **만족도가 더 떨어질 것**
- 하지만 비용 문제로 대형 모델 사용은 **가성비가 낮음**
- SOTA가 아닌 이상 **복잡도 높은 작업은 어차피 못 시킴**
- 그냥 **채팅창으로 단순 질의** 용도로 사용해도 충분

### 6.4. AI가 도움되는 영역

#### AI OCR LLM 활용 사례
```python
# 각 라이브러리 간 데이터 변환 (좌표 변환 등)
# 예: 0~1000 좌표계 → 픽셀 좌표계 변환
```

혼자 개발하면 겪어야 할 시행착오를 LLM의 도움으로 줄일 수 있습니다.
- **소스 스니펫 개발**은 도움받을 만함
- 단순 변환 로직, 보일러플레이트 코드 생성에 효과적

## 7. 조직 관점에서의 시사점

### 7.1. 역할과 책임 (R&R) 문제

#### 질문
AI OCR 등 신기술 POC를 누가 수행해야 하는가?

#### 현황
- 우리는 **기간계시스템 개발/운영** 담당팀
- AI팀은 **AI 기획만** 수행
- 보험회사 내부에서 이런 개발 POC를 자체 수행하는 게 합리적인가?

#### 고민 포인트
- **기술 내재화**가 안 되어서 무조건 아웃소싱이 정답은 아님
- 하지만 조직 역량과 R&R 범위가 불명확
- **업무+IT 융합 인력**의 역할 정립 필요

### 7.2. AA(Application Architect)의 가치

#### 결론
> **업무와 IT를 겸비한 기간계시스템 AA들은 AI에 대체될 수 없는 조직의 필수 인력이다.**

#### AA가 필요한 이유
1. **방향 제시**: AI는 목표를 스스로 설정하지 못함
2. **품질 검증**: AI 결과물을 검수할 수 있는 역량
3. **전체 통합**: 부분 개발물을 전체 시스템으로 통합
4. **업무 맥락**: 실제 비즈니스 요구사항 이해
5. **아키텍처 설계**: 확장성 있는 구조 설계

## 8. 결론

### 8.1. AI 코딩 어시스턴스 활용 핵심 원칙

| 원칙 | 설명 |
|------|------|
| **목표 명시** | "무엇을 위해" 개발하는지 명확히 |
| **설계 선행** | 사람이 직접 설계하고 AI에게 구현 요청 |
| **단계적 검증** | 각 단계마다 검토 → 커밋 → 다음 단계 |
| **버전 관리 필수** | Git 없이는 복구 불가 |
| **모델 간 협업** | 여러 모델 교차 검토로 품질 향상 |
| **사람의 통제** | AI 결과물은 반드시 사람이 검수 |

### 8.2. 최종 메시지

```
AI는 도구일 뿐, 운전자는 사람이다.
```

- AI 코딩 어시스턴스는 **생산성 향상 도구**로서 분명한 가치가 있습니다.
- 하지만 **업무 이해와 IT 역량을 갖춘 전문가**만이 AI를 효과적으로 활용할 수 있습니다.
- **AA(Application Architect)**의 역할은 AI 시대에 더욱 중요해집니다.
- 기간계시스템 전문가는 AI에 대체될 수 없는 **조직의 핵심 인력**입니다.
