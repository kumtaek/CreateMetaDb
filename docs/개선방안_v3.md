
# [개선방안 v3] SQL 관계 분석 로직 리팩토링 상세 계획

## 1. 현황 및 문제점

현재 시스템은 `JOIN_IMPLICIT` 및 `USE_COLUMN` 관계 누락이 심각하며, 그 원인은 여러 파일에 걸친 구조적인 문제에 있다.

### 1.1. 누락 현황

- **`JOIN_IMPLICIT`:** 2건 누락 (정답 5건, 현재 3건)
- **`USE_COLUMN`:** 29건 누락 (정답 100건, 현재 71건)

### 1.2. 근본 원인: 책임과 데이터 흐름의 불일치

**AS-IS (현재의 문제적 흐름):**

1.  **기능의 실질적 마비:** `util/common_sql_processor.py`는 `USE_COLUMN`을 저장하는 함수(`_save_use_column_relationships`)를 가지고 있다. 하지만, 이 함수에 정보를 넘겨줘야 할 `_extract_columns` 함수가 별칭 없는 컬럼(예: `DEPT_ID`)을 아예 추출하지 못한다. 결과적으로 `_save_use_column_relationships` 함수는 **빈 데이터**를 전달받거나 **호출조차 되지 않아** 사실상 마비 상태다.

2.  **기능의 고립:** `inferred column`(DB에 없는 컬럼을 추론하여 등록하는 기능) 생성 로직이, 정작 분석 시점에는 접근할 수 없는 `reports/erd_metadata_service.py`에 고립되어 있다. 이 때문에 `common_sql_processor`는 별칭 없는 컬럼의 주인을 찾지 못해도 `inferred` 처리를 하지 못하고 그냥 누락시킨다.

3.  **책임의 분산:** `xml_loading.py`, `java_parser.py` 같은 개별 파서들이 각자 `common_sql_processor`의 일부 함수를 직접 호출하며 불완전한 관계 생성을 시도한다. 이는 전체 데이터 흐름을 복잡하게 만들고, 오류 발생 시 원인 추적을 어렵게 한다.

**결론: 필요한 부품(함수)들이 각기 다른 서랍에 들어있고, 정작 조립하는 곳(메인 분석 흐름)에서는 어느 서랍에 뭐가 들었는지 몰라 조립을 못 하는 상황이다.**

## 2. 개선 목표

1.  **'누락 Zero' 달성:** `JOIN_IMPLICIT`과 `USE_COLUMN` 관계를 정답지 수준으로 복원한다.
2.  **로직 중앙화 및 재배치:** 파편화된 분석 및 생성 로직을 **메타데이터 생성 단계로 통합**하고, 역할과 책임을 명확히 하여 코드의 구조적 안정성과 유지보수성을 확보한다.

## 3. 해결 전략: `RelationshipBuilder` 중심의 중앙 처리 방식

모든 관계 생성의 책임을 `relationship_builder.py`에 집중시키는 리팩토링을 제안한다.

### TO-BE (개선 후의 명확한 흐름)

1.  **1단계 (부품 모으기):** `reports` 폴더에 있던 `inferred` 생성 로직을 `util/database_utils.py`라는 **공용 부품함**으로 옮긴다.
2.  **2단계 (분석 전문가 재교육):** `common_sql_processor`의 `_extract_` 함수들을 재교육시켜, 별칭이 없거나 불완전한 정보도 **'미완성 부품'** 형태로 빠짐없이 토해내도록 만든다.
3.  **3단계 (최종 조립 라인 구축):** `relationship_builder.py`에 **'최종 조립 라인'**(`_resolve_and_build_relationships`)을 신설한다. 이 조립 라인은 '미완성 부품'을 받아, '공용 부품함'의 `inferred` 부품을 사용해가며 완전한 `JOIN` 및 `USE_COLUMN` 제품으로 조립 후, DB에 최종 납품(저장)한다.
4.  **4단계 (기존 라인 철거):** `xml_loading.py`, `java_parser.py`에 있던 낡고 중복된 조립 라인을 모두 철거하여, 모든 부품이 `relationship_builder`의 새 조립 라인만 거치도록 통일한다.

## 4. 상세 구현 계획

### 4.1. `reports/erd_metadata_service.py` 로직 제거 (선행 작업)

- **대상:** `_save_inferred_columns_to_database` 함수 및 관련 호출 코드.
- **작업:** 해당 코드를 **완전히 제거**한다.

### 4.2. `util/database_utils.py` 기능 추가

- **신규 함수:** `register_inferred_column(self, table_name, column_name)`
- **기능:** `reports`에서 가져온 로직을 기반으로, `columns` 테이블과 `components` 테이블에 `inferred` 컬럼 정보를 원자적으로 `INSERT`한다.

### 4.3. `util/common_sql_processor.py` 리팩토링

- **`_extract_columns` 함수 수정:**
    - **AS-IS:** `('TABLE', 'COLUMN')` 형태의 튜플 리스트 반환. 별칭 없는 컬럼 누락.
    - **TO-BE:** 아래 형태의 **딕셔너리 리스트**를 반환하도록 변경. `alias_map`을 포함시켜 문맥 정보 전달.
      ```python
      # 별칭 없는 컬럼의 경우
      {'table': 'UNKNOWN', 'column': 'DEPT_ID', 'alias_map': {'u': 'USERS', 'd': 'DEPARTMENTS'}}
      ```
- **`_extract_implicit_joins` 함수 수정:**
    - `(+)` 구문을 정규식으로 제거하는 전처리 로직 추가.
    - 별칭 없는 조인 조건(`a.col = col`)도 분석하여, `table`이 `None`으로 채워진 '미완성' 조인 후보 딕셔너리를 생성.

### 4.4. `relationship_builder.py` 기능 강화 (핵심)

- **`build_all_relationships` 함수 수정:**
    - `common_sql_processor.analyze_all_queries()`를 호출하고, 그 결과(미완성 관계 후보 목록)를 신규 메서드에 전달하는 로직 추가.
- **`_resolve_and_build_relationships` 신규 메서드 구현:**
    - **AS-IS:** 기능 부재.
    - **TO-BE:**
      ```python
      def _resolve_and_build_relationships(self, candidates: list[dict]):
          for rel_candidate in candidates:
              # 1. 미완성된 테이블 정보(source/target)가 있는지 확인
              if rel_candidate['source_table'] is None:
                  # 2. 함께 넘어온 alias_map으로 후보 테이블 목록 생성
                  candidate_tables = [t for t in rel_candidate['alias_map'].values() if t != rel_candidate['target_table']]
                  # 3. DB에 직접 쿼리하여 진짜 주인 테이블 탐색
                  owner_table = self._find_owner_table_of_column(rel_candidate['source_column'], candidate_tables)
                  if owner_table:
                      rel_candidate['source_table'] = owner_table # 테이블 확정
                  else:
                      # 4. 주인을 못 찾으면, inferred 처리
                      inferred_table = candidate_tables[0]
                      self.db_utils.register_inferred_column(inferred_table, rel_candidate['source_column'])
                      rel_candidate['source_table'] = inferred_table
              
              # (target_table이 None인 경우도 동일하게 처리)

              # 5. 최종 확정된 정보로 JOIN 및 USE_COLUMN 관계를 DB에 저장
              if rel_candidate['source_table'] and rel_candidate['target_table']:
                  # JOIN 관계 저장
                  self._insert_relationship(...)
                  # USE_COLUMN 관계 2건 저장 (source/target)
                  self._insert_relationship(...)
                  self._insert_relationship(...)
      ```

### 4.5. `java_parser.py`, `xml_loading.py` 단순화

- **AS-IS:** 각 파일에서 `common_sql_processor`의 내부 함수들을 직접 호출하며, 불완전한 관계 생성을 시도하는 복잡한 로직 존재.
- **TO-BE:** 해당 로직들을 **모두 제거**한다. 이제 이 파서들은 `main.py`의 흐름에 따라 SQL 추출 및 `SqlContent.db` 저장 역할만 수행하면 된다.

## 5. 기대 효과

- **누락 문제 해결:** 별칭 없는 컬럼, `(+)` 구문 등 기존에 처리하지 못했던 모든 케이스를 커버하여 `JOIN_IMPLICIT`과 `USE_COLUMN` 누락 문제를 근본적으로 해결한다.
- **유지보수성 향상:** 복잡하고 파편화되었던 관계 생성 및 `inferred` 처리 로직이 `relationship_builder.py`와 `database_utils.py`로 중앙화되어, 향후 수정 및 디버깅이 매우 용이해진다.
- **명확한 데이터 흐름:** `파서(추출) -> 분석기(후보 생성) -> 빌더(확정 및 저장)`로 데이터 흐름이 명확해져 코드 전체의 이해도가 높아진다.
