# ERD 관계선 방향 개선 이력 (2025-11-26)

## 개요
ERD 리포트에서 PK-FK 관계의 방향(닭발)이 올바르게 표시되지 않는 문제를 해결

## 문제점

### 증상
- DEPARTMENTS.DEPT_ID (PK) ↔ USERS.DEPT_ID (FK) 관계에서 `USERS ||--o{ DEPARTMENTS`로 잘못 표시
- PRODUCTS.PRODUCT_ID (PK) ↔ ORDER_ITEMS.PRODUCT_ID (FK) 관계에서 `ORDER_ITEMS ||--o{ PRODUCTS`로 잘못 표시
- Mermaid ERD의 `A ||--o{ B` 문법은 A(1) : B(N) 관계를 의미하므로, PK가 있는 쪽이 왼쪽에 와야 함

### 원인
- 기존 코드는 데이터베이스의 relationships 테이블에 저장된 src→dst 방향을 그대로 사용
- PK-FK 관계를 고려하지 않고 조인 관계의 저장 순서만 반영
- `_get_relationship_info` 메서드가 INFERRED 컬럼의 경우 PK 정보를 찾지 못함

## 해결 방법

### 1. PK-FK 관계 판단 로직 추가 (`_get_relationship_info` 메서드)

#### 변경 전
```python
def _get_relationship_info(self, src_table: str, src_column: str, dst_table: str, dst_column: str) -> dict:
    rel_info = self.metadata_service.get_relationship_info(src_table, src_column, dst_table, dst_column)
    return {
        'is_pk_fk': (rel_info['src_is_pk'] and not rel_info['dst_is_pk']) or
                   (not rel_info['src_is_pk'] and rel_info['dst_is_pk']),
        'src_nullable': rel_info['src_nullable'],
        'dst_nullable': rel_info['dst_nullable']
    }
```

#### 변경 후
```python
def _get_relationship_info(self, src_table: str, src_column: str, dst_table: str, dst_column: str) -> dict:
    """관계 정보 확인 - 공용 서비스 사용, INFERRED 컬럼의 경우 PK 조회로 추론"""
    # [I] 접두어 제거 (INFERRED 테이블 처리)
    src_table_clean = src_table[3:] if src_table.startswith('[I]') else src_table
    dst_table_clean = dst_table[3:] if dst_table.startswith('[I]') else dst_table

    rel_info = self.metadata_service.get_relationship_info(src_table_clean, src_column, dst_table_clean, dst_column)

    # 컬럼 정보를 찾지 못한 경우 (INFERRED 컬럼 등), 각 테이블의 PK 조회로 추론
    if not rel_info['src_is_pk'] and not rel_info['dst_is_pk']:
        # 각 테이블의 PK 컬럼명 조회
        src_pk_column = self._get_table_pk_column(src_table_clean)
        dst_pk_column = self._get_table_pk_column(dst_table_clean)

        # src_column이 dst 테이블의 PK와 동일하면 dst가 PK, src가 FK
        if dst_pk_column and src_column.upper() == dst_pk_column.upper():
            rel_info['dst_is_pk'] = True
            rel_info['src_is_pk'] = False
        # dst_column이 src 테이블의 PK와 동일하면 src가 PK, dst가 FK
        elif src_pk_column and dst_column.upper() == src_pk_column.upper():
            rel_info['src_is_pk'] = True
            rel_info['dst_is_pk'] = False

    return {
        'is_pk_fk': (rel_info['src_is_pk'] and not rel_info['dst_is_pk']) or
                   (not rel_info['src_is_pk'] and rel_info['dst_is_pk']),
        'src_nullable': rel_info['src_nullable'],
        'dst_nullable': rel_info['dst_nullable'],
        'src_is_pk': rel_info['src_is_pk'],
        'dst_is_pk': rel_info['dst_is_pk']
    }
```

### 2. PK 컬럼명 조회 메서드 추가 (`_get_table_pk_column`)

```python
def _get_table_pk_column(self, table_name: str) -> str:
    """테이블의 PK 컬럼명 조회"""
    try:
        query = """
            SELECT c.column_name
            FROM columns c
            JOIN tables t ON c.table_id = t.table_id
            JOIN projects p ON t.project_id = p.project_id
            WHERE t.table_name = ?
              AND p.project_name = ?
              AND c.position_pk IS NOT NULL
              AND t.del_yn = 'N'
              AND c.del_yn = 'N'
            ORDER BY c.position_pk
            LIMIT 1
        """
        result = self.db_utils.execute_query(query, (table_name.upper(), self.project_name))
        return result[0]['column_name'] if result else None
    except Exception as e:
        app_logger.error(f"PK 컬럼 조회 실패: {table_name}, {str(e)}")
        return None
```

### 3. Mermaid ERD 생성 시 방향 결정 로직 수정

#### 변경 전
```python
# ERD는 단순 문법만 지원: A ||--o{ B : has 형태만 사용
# PK-FK 관계든 JOIN 관계든 동일한 문법 사용
mermaid_lines.append(f'    "{src_table}" ||--o{{ "{dst_table}" : {relationship_label}')
```

#### 변경 후
```python
# ERD 관계 방향 결정: PK가 있는 쪽이 1(왼쪽), FK가 있는 쪽이 N(오른쪽)
# Mermaid 문법: A ||--o{ B 는 A(1) : B(N) 관계를 의미
if rel_info['src_is_pk'] and not rel_info['dst_is_pk']:
    # src가 PK, dst가 FK → src(1) : dst(N)
    one_side = src_table
    many_side = dst_table
elif not rel_info['src_is_pk'] and rel_info['dst_is_pk']:
    # src가 FK, dst가 PK → dst(1) : src(N)
    one_side = dst_table
    many_side = src_table
else:
    # PK-FK 관계가 명확하지 않은 경우, 기본적으로 src → dst 방향 사용
    one_side = src_table
    many_side = dst_table

# ERD는 단순 문법만 지원: A ||--o{ B : has 형태만 사용
mermaid_lines.append(f'    "{one_side}" ||--o{{ "{many_side}" : {relationship_label}')
```

## 추가 개선 (2025-11-26 오후)

### 문제점 2: 3단계 우선순위 로직 미적용

#### 증상
- ORDERS.ORDER_ID (PK) ↔ BRAND_METRICS.ORDER_ID 관계에서 여전히 방향이 반대로 표시됨
- `BRAND_METRICS ||--o{ ORDERS` 대신 `ORDERS ||--o{ BRAND_METRICS`가 되어야 함
- INFERRED 테이블의 조인 컬럼을 무조건 PK로 가정하는 오류

#### 원인
사용자 요구사항:
> "BRANDS.BRAND_ID (PK, INFERRED 컬럼) -> 이게 PK인지는 알수가 없어 불필요한 유추로 만들지마. 다만 코드성 테이블은 CSV에 미정의일 수 있으니 PK쪽이 있으면 1로 보고, 아니고 조인키가 PK가 아닌데 다른 PK가 있으면 그쪽을 N으로 보고 다른 PK가 있으으로 FK가 되는것임. 둘다 PK가 없으면 방금전 INFERRED로 도출된 쪽을 1로 보도록 하자."

기존 로직은 단순히 조인 컬럼의 PK 여부만 확인했으나, 다음 3단계 우선순위 로직이 필요:
1. **우선순위 1**: 조인 컬럼 자체가 PK인 경우 → 그쪽이 1(one)
2. **우선순위 2**: 조인 컬럼이 PK가 아닌데, 테이블에 다른 PK가 있는 경우 → 그쪽이 N(many), 반대쪽이 1(one)
3. **우선순위 3**: 둘 다 다른 PK가 없는 경우 → INFERRED 테이블이 1(one), 실제 테이블이 N(many)

### 해결 방법: 3단계 우선순위 로직 구현

#### 파일: `reports/erd_report_generator.py` (lines 334-398)

3단계 우선순위 로직을 `_get_relationship_info` 메서드에 구현하고, `_has_other_pk` 헬퍼 메서드를 추가하여 테이블에 조인 컬럼 외 다른 PK가 있는지 확인

### 문제점 3: `get_relationship_info` JOIN 쿼리 실패

#### 증상
- 조인 컬럼명이 양쪽 테이블에서 다른 경우 (예: ORDER_ID ↔ ORDER_REF) 관계 정보 조회 실패
- INFERRED 컬럼의 경우 columns 테이블에 존재하지 않아 JOIN 결과 없음
- 기본값(모두 False)이 반환되어 우선순위 3 로직이 잘못 적용됨

#### 원인
기존 `get_relationship_info`는 하나의 JOIN 쿼리로 src와 dst 컬럼을 동시에 조회하여, 컬럼명이 다르거나 존재하지 않으면 결과가 없었음

### 해결 방법: 각 컬럼 별도 조회

#### 파일: `reports/erd_metadata_service.py` (lines 812-874)

src 컬럼과 dst 컬럼을 각각 별도 쿼리로 조회하여, 한쪽 컬럼이 없더라도 다른 쪽 정보는 정상 조회 가능하도록 개선

### 검증 결과

#### 우선순위 1 적용 케이스
- `ORDERS ||--o{ [I]PAYMENTS` ✅ (ORDERS.ORDER_ID가 PK)
- `ORDERS ||--o{ [I]INVENTORY_AUDIT` ✅ (ORDERS.ORDER_ID가 PK)

#### 우선순위 2 적용 케이스
- `[I]BRANDS ||--o{ PRODUCTS` ✅ (PRODUCTS에 PRODUCT_ID라는 다른 PK 존재)
- `DEPARTMENTS ||--o{ USERS` ✅ (USERS에 USER_ID라는 다른 PK 존재)

#### 우선순위 3 적용 케이스
- INFERRED 테이블이 1(one), 실제 테이블이 N(many)로 정상 표시
