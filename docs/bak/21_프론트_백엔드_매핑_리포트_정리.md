# 프론트/백엔드 매핑 리포트 최신 정리

## 공통 원칙
- 메타DB/SqlContentDB는 재파싱 없이 이미 적재된 데이터만 사용.
- API_URL/쿼리 등은 `component_id` 기준으로 매핑하여 동일 이름의 다른 파일이 섞이지 않도록 한다.
- DB 접근은 `DatabaseUtils` 지속 커넥션을 사용하고, 닫힌 커넥션은 `_ensure_connection`으로 재연결.

## sqltext 처리
- 경로: `projects/{project}/sqltext/**/*.sql` 재귀 스캔.
- components: 내용으로 쿼리 타입 결정(`SQL_SELECT/INSERT/UPDATE/DELETE/MERGE` 등), layer=`QUERY_FROM_SQLTEXT`, component_name=파일명.
- SqlContent: query_id=파일명, layer=`QUERY_FROM_SQLTEXT` 저장.
- Java 매칭: `component_type LIKE 'SQL%' AND layer='QUERY_FROM_SQLTEXT'` 대상, `component_id`로 CALL_QUERY 매핑.

## API/메서드 매핑
- API_URL 생성/조회는 identity_hash 기반(프론트/백 동일 규칙), 프론트 발견 시 file_id를 프론트 파일로 갱신하되 기존 값은 유지 보호.
- Backend entry(Spring/Servlet) 파서는 클래스/메서드 URL을 합성해 API_URL 생성, CALL_METHOD는 파일·메서드명 기준 매칭 후 fallback 없이 연결.
- frontend_mapping_report: 프론트→API_URL→METHOD→QUERY 체인을 metadata만으로 시각화.

## Backend Mapping Report (정렬/매핑 기준)
- SqlContent 조회 시 `component_id` 포함.
- USE_TABLE/조인 정보는 metadata에서 `component_id` 기준으로 적재·매핑(쿼리명이 같아도 파일별 테이블이 섞이지 않음).
- 출력 컬럼: Path/File/Method(QueryID)/SQL 타입/테이블/조인조건/조인타입.

## Frontend Mapping Report
- Backend Mapping Report와 동일 톤/스타일(컨테이너/테이블 CSS).
- 컬럼: No, Frontend, Frontend File, API URL, Method, Method File, Query ID.

## 로그/스로틀
- 반복 WARN(예: METHOD 없음 등)은 1초 스로틀링으로 콘솔 스팸 방지. 로그 파일에는 기록 유지.
