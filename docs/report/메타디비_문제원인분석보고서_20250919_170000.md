## 1. 근본 원인 분석

### 1.1 파일 중복 처리 문제 (Root Cause #1)

#### 발견된 중복 현황
```
UserMapper.xml이 4번 중복 등록:
- file_id=6: src\com\example\dynamicquery\UserMapper.xml (33개 컴포넌트)
- file_id=69: src\main\resources\mybatis\mapper\UserMapper.xml (28개 컴포넌트)  
- file_id=91: src/com/example/dynamicquery/UserMapper.xml (10개 컴포넌트)
- file_id=154: src/main/resources/mybatis/mapper/UserMapper.xml (28개 컴포넌트)
총 99개 컴포넌트 (실제는 17개 쿼리만 있음)
```

#### 중복 발생 메커니즘 (정확한 원인 파악)

**1단계: file_loading.py 파일 스캔**
```python
# 1단계에서 파일 등록 (Windows 경로 그대로)
src\com\example\dynamicquery\UserMapper.xml (file_id=6)
src\main\resources\mybatis\mapper\UserMapper.xml (file_id=69)
```

**3단계: xml_loading.py XML 분석**  
```python
# 3단계에서 같은 파일을 다시 등록 (Unix 경로로 정규화)
src/com/example/dynamicquery/UserMapper.xml (file_id=91)  
src/main/resources/mybatis/mapper/UserMapper.xml (file_id=154)
```

**중복 발생 정확한 원인**:
1. **1단계와 3단계 독립 실행**: 각 단계가 파일을 독립적으로 등록
2. **경로 정규화 시점 차이**: 1단계(Windows 경로), 3단계(Unix 경로)
3. **중복 체크 로직 부재**: 기존 파일 존재 여부 확인 없이 신규 등록
4. **main.py 설계 문제**: 각 단계가 독립적으로 파일을 처리하는 구조

**결과**: UserMapper.xml 하나가 4개의 다른 file_id로 등록됨

### 1.2 관계 방향 오류 문제 (Root Cause #2)

#### 현재 관계 생성 로직 문제
**ERDMetadataService.get_relationships()**: 
```python
# 현재 잘못된 로직
SELECT DISTINCT
    r.rel_type,
    src_table.table_name as src_table,    # 실제로는 SQL 쿼리
    dst_table.table_name as dst_table     # 실제로는 테이블
FROM relationships r
JOIN components src_sql ON r.src_id = src_sql.component_id      # SQL 컴포넌트
JOIN components dst_table_comp ON r.dst_id = dst_table_comp.component_id  # 테이블 컴포넌트
```

**문제점**:
1. **src/dst 의미 혼동**: SQL→TABLE 관계에서 SQL이 src, TABLE이 dst인데 이를 테이블 간 관계로 해석
2. **관계 방향 역전**: 실제 외래키 관계와 반대 방향으로 표시
3. **복잡한 조인**: 불필요하게 복잡한 조인으로 인한 혼동

#### 올바른 관계 생성 로직
```python
# 외래키 기반 관계 생성이 필요
SELECT 
    parent_table.table_name as parent_table,  # 외래키가 참조하는 테이블 (부모)
    child_table.table_name as child_table,    # 외래키를 가진 테이블 (자식)
    fk_col.column_name as join_column
FROM columns fk_col
JOIN tables child_table ON fk_col.table_id = child_table.table_id
JOIN columns pk_col ON fk_col.referenced_column_id = pk_col.column_id
JOIN tables parent_table ON pk_col.table_id = parent_table.table_id
WHERE fk_col.is_foreign_key = 1
```

### 1.4 USER_ROLE 관계 누락 원인

#### 실제 스키마 vs 메타디비 분석
**실제 스키마** (ALL_TABLES.csv):
```

```


2. **관계 추출 실패**: USER_ROLE과 USERS 간 관계가 XML에서 추출되지 않음
3. **외래키 정보 부족**: USER_ROLE 테이블의 외래키 정보가 누락

## 3. 구체적 문제 사례 분석

### 3.1 UserMapper.xml 중복 처리 사례

#### 중복 등록 과정
```
1. file_loading.py: src\main\resources\mybatis\mapper\UserMapper.xml (file_id=6)
2. xml_loading.py: src/main/resources/mybatis/mapper/UserMapper.xml (file_id=82)
   - 경로 정규화로 다른 파일로 인식
   - 28개 컴포넌트 중복 생성
   - 모든 관계 중복 생성
```

#### 영향
- **컴포넌트 중복**: 28개 × 2 = 56개
- **관계 중복**: 모든 USE_TABLE, JOIN 관계 2배 생성
- **통계 왜곡**: 실제보다 2배 많은 데이터

### 3.2 NONEXISTENT_TABLE 처리 사례

#### 잘못된 테이블 생성 과정
```xml
<!-- MixedErrorMapper.xml -->
<select id="selectFromNonExistentTable">
    SELECT id, name, email
    FROM NONEXISTENT_TABLE  <!-- 테스트용 가상 테이블 -->
    WHERE id = #{id}
</select>
```

**메타디비 처리**:
1. SQL 파싱에서 NONEXISTENT_TABLE 추출
2. 스키마 검증 없이 TABLE 컴포넌트 생성
3. USE_TABLE 관계 생성
4. ERD에 가상 테이블로 표시

**문제**: 실제 존재하지 않는 테이블도 정상 테이블로 처리

### 3.3 USER_ROLE vs USER_ROLES 혼동 사례

#### 실제 상황
**실제 스키마**: `PUBLIC.USER_ROLE` (사용자역할 테이블)
**XML에서 추론**: `USER_ROLES` (가상 테이블)

**메타디비 처리**:
```
1. ALL_TABLES.csv에서 USER_ROLE 테이블 생성 (실제)
2. UserMapper.xml에서 USER_ROLES 테이블 추론 (가상)
3. USERS -> USER_ROLES 관계 생성 (가상 관계)
4. USER_ROLE은 관계 없는 고아 테이블로 분류
```

**문제**: 테이블명 유사성으로 인한 혼동, 실제 관계 누락
