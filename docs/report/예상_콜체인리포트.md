# 콜체인 리포트 정답지 (sampleSrc)

## 개요

본 문서는 **sampleSrc 프로젝트의 소스 코드를 직접 분석**하여 콜체인 리포트가 **정확히 어떻게 생성되어야 하는지**에 대한 정답지입니다. 이 정답지와 실제 메타디비 시스템이 생성한 콜체인 리포트를 비교하여 시스템의 정확성을 검증합니다.

**작성 기준**: sampleSrc 소스 파일 직접 분석  
**분석 일시**: 2025-09-19  
**호출 체인 패턴**: JSP/JSX → API_URL → Controller → Service → DAO → (MyBatis Mapper | Direct SQL) → TABLE  
**분석 결과**:
- 프론트엔드 페이지: 17개 (JSP 12개 + JSX 5개)
- API 엔드포인트: 43개
- Java 클래스: 51개 (컨트롤러, 서비스, DAO 포함)
- SQL 쿼리: 193개
- 테이블: 64개 (실제 17개 + 추론 47개)

## 예상 호출 패턴 분석

### 1. 표준 3-tier 패턴
```
JSP → Controller → Service → DAO → MyBatis → Database
```
- 가장 일반적인 패턴
- 전체 콜체인의 80% 이상

### 2. 직접 DAO 호출 패턴
```
JSP → Controller → DAO → MyBatis → Database
```
- Service 레이어를 건너뛰는 패턴
- 단순한 CRUD 작업에서 사용

### 3. 복잡한 비즈니스 로직 패턴
```
JSP → Controller → Service → [비즈니스 로직] → DAO → MyBatis → Database
```
- 데이터 검증, 가공, 통계 계산 등을 포함
- 사용자 통계, 복잡한 검색에서 사용

## 예상 JOIN 관계 분석

### 1. USERS-ORDERS 관계
- **JOIN 타입**: LEFT JOIN
- **조인 조건**: u.user_id = o.user_id
- **사용 쿼리**: findUsersWithOrderInfo, findUsersByComplexSearch
- **관계 타입**: JOIN_EXPLICIT

### 2. PRODUCTS-CATEGORIES 관계
- **JOIN 타입**: LEFT JOIN
- **조인 조건**: p.category_id = c.category_id
- **사용 쿼리**: selectProductsByAdvancedCondition
- **관계 타입**: JOIN_EXPLICIT

### 3. PRODUCTS-BRANDS 관계
- **JOIN 타입**: LEFT JOIN
- **조인 조건**: p.brand_id = b.brand_id
- **사용 쿼리**: selectProductsByAdvancedCondition
- **관계 타입**: JOIN_EXPLICIT

### 4. USERS-USER_PROFILES 관계
- **JOIN 타입**: INNER JOIN
- **조인 조건**: u.user_id = up.user_id
- **사용 쿼리**: getUserById (마이크로서비스)
- **관계 타입**: JOIN_EXPLICIT

## 검증 포인트

실제 CallChainReport 생성 후 다음 항목들을 검증해야 합니다:

### 1. 콜체인 완성도
- [ ] 예상된 27개의 콜체인이 모두 생성되었는가?
- [ ] JSP → API_URL → METHOD → SQL → TABLE 연결이 완전한가?
- [ ] 누락된 호출 관계는 없는가?

### 2. API_URL 매핑 정확성
- [ ] JSP에서 호출하는 API URL이 올바르게 추출되었는가?
- [ ] HTTP 메서드(GET, POST, PUT, DELETE)가 정확한가?
- [ ] 동적 URL 패턴({id}, {type})이 올바르게 처리되었는가?

### 3. 메서드 연결 정확성
- [ ] Controller 메서드가 올바른 Service 메서드를 호출하는가?
- [ ] Service 메서드가 올바른 DAO 메서드를 호출하는가?
- [ ] DAO 메서드가 올바른 MyBatis 쿼리를 호출하는가?

### 4. SQL 쿼리 매핑 정확성
- [ ] MyBatis 쿼리 ID가 올바르게 추출되었는가?
- [ ] SQL 타입(SELECT, INSERT, UPDATE, DELETE)이 정확한가?
- [ ] 동적 SQL 조건이 올바르게 분석되었는가?

### 5. JOIN 관계 분석 정확성
- [ ] LEFT JOIN 관계가 JOIN_EXPLICIT로 분류되었는가?
- [ ] 조인 조건이 올바르게 추출되었는가?
- [ ] 복잡한 서브쿼리 JOIN이 올바르게 분석되었는가?

### 6. 테이블 사용 관계 정확성
- [ ] 각 SQL 쿼리에서 사용하는 테이블이 올바르게 식별되었는가?
- [ ] 별칭(alias)이 실제 테이블명으로 올바르게 변환되었는가?

## 예상 이슈 및 대응

### 1. 동적 SQL 처리
- **이슈**: `<if>`, `<choose>` 태그로 인한 조건부 테이블 참조
- **예상**: 모든 가능한 테이블이 관계에 포함되어야 함
- **검증**: 동적 조건의 모든 경우가 고려되었는지 확인

### 2. 복잡한 JOIN 쿼리
- **이슈**: 서브쿼리 내의 JOIN 관계
- **예상**: 서브쿼리의 JOIN도 별도 관계로 추출되어야 함
- **검증**: 중첩된 쿼리의 모든 JOIN이 분석되었는지 확인

### 3. StringBuilder SQL
- **이슈**: Java 코드 내의 동적 SQL 생성
- **예상**: StringBuilder로 생성된 SQL도 분석되어야 함
- **검증**: UserDao.findUsersByDirectQuery의 SQL이 추출되었는지 확인

### 4. API URL 패턴 매칭
- **이슈**: RESTful URL 패턴의 동적 부분
- **예상**: `/user/dynamic/{type}` → `/user/dynamic/ADMIN` 등으로 구체화
- **검증**: 동적 URL이 올바르게 처리되었는지 확인

## 결론

예상되는 콜체인 리포트는 sampleSrc 프로젝트의 완전한 호출 흐름을 보여주며, 다음과 같은 특징을 가집니다:

3. **동적 SQL 활용**: MyBatis를 통한 조건부 쿼리 생성
4. **RESTful API 설계**: HTTP 메서드별 명확한 엔드포인트 구분
