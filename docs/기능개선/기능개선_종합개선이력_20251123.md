## 2. 초기 문제 인식 – 메타DB 품질 문제

### 2.1 중복 데이터 문제

`DEL_1.중복,파싱능력부족보고서.md` 기준:

- **SQL 컴포넌트 통계**
  - 총 SQL 컴포넌트: **127개**
  - 고유 SQL 이름: **82개**
  - 중복 수: **45개 (중복률 약 35.4%)**
- 주요 중복 예시
  - `countProductsByCondition`, `countUsers`, `deleteProductsByCondition`, `findComplexJoins`, `findUsers` 등 대부분의 핵심 쿼리가 **2배로 집계**

### 2.2 중복 원인

- **파일 등록 중복**
  - 동일 XML 파일이 서로 다른 `file_id` 로 여러 번 등록됨
  - 예: `ProductMapper.xml`, `UserMapper.xml`, `ImplicitJoinMapper.xml` 등이 2개 이상의 `file_id` 로 존재
- **증분 분석 시 정리 부재**
  - 기존 메타DB를 깨끗이 비우지 않고, **추가 INSERT** 만 수행 → 과거 데이터 + 신규 데이터가 함께 쌓여 수치 부풀림
- **경로 정규화 문제**
  - 같은 파일이라도 경로 표기(구분자/루트경로)에 따라 **서로 다른 파일로 인식**
  - Windows/Unix 혼합 경로, 상대/절대 경로 등으로 인한 **Path 식별 불일치**
- **중복 방지 로직 미비**
  - 파일 해시 기반 중복 체크가 제대로 동작하지 않거나, 로직이 분산되어 있어 **일관된 중복 방지 정책이 부재**

### 2.3 중복이 초래한 영향

- 통계 왜곡
  - 실제 82개 쿼리가 127개로 보이며, **리포트의 신뢰도가 크게 떨어짐**
  - 조인 관계도 동일 관계가 2번 이상 중복 저장되어, ERD/리포트에서 “관계가 과장”되어 보임
- 성능 및 관리 비용 증가
  - 불필요한 데이터로 인한 저장공간 낭비
  - 리포트 생성 시 중복 제거/후처리에 추가 오버헤드 발생

> **교훈 1**  
> 메타DB는 “한 번 더 넣어도 되겠지”가 아닌, **멱등성을 강하게 보장해야 하는 데이터베이스**다.  
> 파일 스캔·해시·UNIQUE 제약·INSERT OR IGNORE 전략을 통해 **중복을 구조적으로 차단**해야 한다.

## 3. 파싱 능력의 범위와 한계 – 어디까지 할 것인가?

초기 분석 결과와 개선계획(`DEL_1.중복,파싱능력부족보고서.md`)에서, “이론적으로 가능한 모든 SQL/Java 패턴을 다 지원하겠다”라는 목표는 **현실적으로 불가능하거나 비용 대비 이득이 낮다**는 결론에 도달했습니다.

### 3.1 XML(MyBatis) 지원 범위

요약 기준 (세부 수치는 보고서 참고):

- **완전 지원 (필수)**
  - `SELECT / INSERT / UPDATE / DELETE` 기본 쿼리
  - `EXPLICIT JOIN` (ANSI JOIN)
  - `IMPLICIT JOIN` (Oracle 스타일)
- **부분 지원 (중요하지만 100% 목표는 아님)**
  - 동적 SQL (`<if>`, `<choose>`, `<where>` 등) 내부의 테이블/조인
  - 복잡한 서브쿼리 (중첩 구조)
  - CTE(`WITH`) 기본 패턴
- **의도적 미지원 또는 제한 지원 (ROI 낮음)**
  - 완전 일반화된 `MERGE ... USING ... ON ...` 모든 변형
  - 다단계 재귀 CTE
  - 런타임에만 확정되는 동적 테이블명 (예: `${schemaName}.${tableName}`)

> **핵심 포인트**  
> 테이블/컬럼이 **누락 없이** 도출되는 것이 우선이며,  
> 모든 JOIN 조건을 100% “읽을 수 있게” 표현하는 것은 그 다음이다.

### 3.2 Java SQL 지원 범위

보고서 기준 정리:

- **우선 지원 대상**
  - `StringBuilder` 기반 SQL 조립 패턴 → 현재 **주요 패턴은 지원**
  - MyBatis Mapper 메서드 호출 → METHOD → QUERY 매핑
- **부분/제한 지원 대상**
  - `+` 연산자 기반 문자열 결합 (변수 추적까지 완벽히 하지는 않음)
  - `String.format` 기반 템플릿 쿼리
  - 조건부 분기(if/else) 내 SQL
- **사실상 비현실적인 목표**
  - 복잡한 제어 흐름(루프/복잡한 조건)에 따라 동적으로 조립되는 모든 쿼리의 “실제 실행 경로”를 정적 분석만으로 100% 맞추는 것

> **교훈 2**  
> Java 쪽은 “SQL 문자열이 눈에 보이는 만큼만 최대한 커버” 하되,  
> **제어 흐름까지 완전 추적하는 정적 분석기는 이 프로젝트 범위를 넘어선다**는 점을 인정하고 설계해야 한다.

## 4. MyBatis Enhanced 파서 실패와 타협안

`DEL_개발불가_사유분석보고서.md`, `DEL_테스트결과보고서_1차.md` 에서 정리된 **실패 사례와 최종 설계 선택**입니다.

### 4.1 동적 SQL 완전 분기 탐색 시도의 실패

- 초기 목표
  - `<if>` 태그를 모두 True/False 조합으로 펼쳐서 **가능한 모든 SQL 버전**을 생성 후, 각 버전별로 테이블/조인을 추출
- 실제 문제점
  - `<if>` 가 n개면 경로 수는 `2^n` 으로 폭증 → **조합 폭발**
  - 실무 XML 파일에서 `<if>` 가 9개인 경우, 최대 512개 SQL 버전 생성
  - 메모리 사용량/처리시간이 **실용 범위를 초과** (단일 파일 120초 이상)
  - 이론적으로 가능한 조합 중 실제로는 발생할 수 없는 조합까지 생성하여, 오히려 분석 결과를 **왜곡**

### 4.2 `<include>` 태그 풀스펙 지원 시도의 실패

- 원래 계획
  - 모든 `<sql id="...">` 조각을 전역 캐시에 수집
  - `<include refid="...">` 발견 시 실제 SQL 조각으로 치환
  - 재귀적 include, 크로스 파일 include 까지 모두 지원
- 실패 사례
  - 순환 include (`fragmentA` → `fragmentB` → 다시 `fragmentA`) 로 인해 **무한 재귀/stack overflow**
  - 3~4단계 이상 크로스 파일 include 시, 네임스페이스·성능·재귀 한계 이슈가 동시에 발생
  - 재귀 제한을 높이면 다른 XML/설정 파싱에 부작용 발생

### 4.3 Enhanced 파서 1차 테스트 결과 (실패)

`DEL_테스트결과보고서_1차.md` 요약:

- 테스트용 XML/Java 파일 5개를 `testcase` 폴더에 추가하고 전체 분석 실행
- 결과
  - Enhanced 파서: 재귀 문제로 **모든 XML에서 실패**
  - Fallback 기본 파서: 호출은 되었으나 설정/초기화 문제로 **SQL 컴포넌트 0개 추출**
  - 결국 **기본 기능까지 망가진 상태**가 되어 실사용 불가 판단

### 4.4 최종 타협안 – “안전한 제한형 Enhanced + Fallback”

개발불가 보고서에서 도출된 최종 방향:

- **분석 깊이·경로 수 제한**
  - 동적 SQL 분석 깊이(`max_dynamic_depth`), 경로 수(`max_paths`)를 설정값으로 제한
  - 가장 짧은 경로(기본), 가장 긴 경로(조건 모두 포함), 몇 개의 대표적인 중간 경로만 선택
- **위험도가 높은 패턴 제외**
  - 순환 include 의심 파일, 테스트용 특수 패턴은 설정에서 제외
- **항상 존재하는 안전한 Fallback**
  - Enhanced 파서 실패 시 무조건 **기존 MyBatis 파서로 되돌아감**
  - 예외가 상위로 전파되어 전체 시스템이 죽는 일이 없도록 방지
- **하드코딩 금지, 설정 기반 제어**
  - depth/paths/제외 대상 파일들은 모두 YAML 설정으로 외부화
  - 프로젝트별로 부담 가능한 수준으로 튜닝 가능

> **교훈 3**  
> “이론적으로는 가능한 완전한 분석”보다는  
> **제한을 두더라도 안정적으로 돌아가는 분석**이 훨씬 가치가 크다.  
> 새 기능은 **기본 기능을 절대 깨지 않는 선**에서만 도입해야 한다.

## 5. 연관관계 도출 아키텍처의 발전

`DEL_개선소스리뷰 및 개선안제안.md` 는 최종 상태 기준으로 **“연관관계 도출 시스템이 어디까지 구현되었는지”**를 정리한 문서입니다.

### 5.1 최종 목표 체인

최종적으로 달성하려 한/달성한 분석 체인:

`프론트 파일 (JSP/JSX/Vue/TS/JS)`  
→ `API_URL (프론트에서 호출되는 URL)`  
→ `Controller / Servlet METHOD (Spring/Servlet 진입점)`  
→ `MyBatis Mapper METHOD or JPA Repository`  
→ `XML / Java 내 SQL`  
→ `TABLE / COLUMN`

보고서 기준 평가:

- XML → QUERY → TABLE: 약 **95% 수준**
- Java METHOD → QUERY: 약 **90% 수준**
- JPA ENTITY → TABLE: 약 **85% 수준**
- 프론트 → API_URL: 약 **85% 수준**
- API_URL → METHOD: 약 **80% 수준**
- 전체 체인: **약 85% 수준의 완성도**

즉, “누락없는 대략적 분석”이라는 목표 관점에서는 **충분히 실용적인 수준**으로 도달했다는 평가입니다.

### 5.2 RelationshipBuilder 패턴

- `relationship_builder.py` 의 실제 역할 (현행 소스 기준)
  - 각 단계별 로딩 엔진(XML/Java/프론트엔드/백엔드 엔트리 등)은 **자신이 파싱한 결과를 바로 메타DB에 기록**합니다.
    - 예: `frontend_loading.py` 는 API_URL 컴포넌트와 CALL_API 관계를 즉시 `components`/`relationships` 에 INSERT
    - Java 로더/파서는 METHOD, SQL\_* 컴포넌트를 생성
    - SqlContent 저장 로직은 SqlContent.db에 정제된 SQL을 저장
  - `RelationshipBuilder` 는 이 **이미 저장된 메타DB/SqlContent.db 데이터를 기반으로만** 연관관계를 생성하는 **중앙 빌더**입니다.
    - `API_URL → METHOD` : 파일 ID 기반 정밀 매칭 (`_build_api_method_from_file_id`)
    - `API_URL → METHOD` : HTTP:methodName 패턴을 이용한 보수적 폴백 (`_build_frontend_api_relationships`)
    - `METHOD → SQL_*` : MyBatis FQMN 기반 정밀 매칭 (`_build_mybatis_fqmn_relationships`)
    - `METHOD → SQL_*` : 메서드명 == SQL ID 패턴을 이용한 보수적 폴백 (`_build_method_query_by_name_fallback`)
    - 이후 `CommonSqlAnalyzer.analyze_all_queries()` 호출로 `QUERY → TABLE`, `TABLE ↔ TABLE (JOIN)` 관계를 생성
- 장점
  - **Parser/Loader (DB에 단서 저장)** 와 **RelationshipBuilder (저장된 단서로 관계 조립)** 가 명확히 분리되어 있어, 어느 단계에서 문제가 생겼는지 추적하기 쉽습니다.
  - 새로운 유형의 컴포넌트나 관계를 추가할 때도,  
    - 1단계: 해당 로더가 DB에 필요한 최소 정보를 저장
    - 2단계: `RelationshipBuilder` 에서 그 정보를 읽어 새로운 관계를 추가  
    라는 패턴으로 확장할 수 있어, 구조가 단순하게 유지됩니다.

### 5.3 프론트엔드 API 분석기

- 위치: `util/frontend_api_analyzer.py`
- 역할
  - Axios / Fetch / jQuery / Vue Resource 등에서 **URL 문자열을 추출**
  - 파일 경로, 라인 정보와 함께 `API 호출 기록`으로 저장
- 한계
  - 정규식 기반으로 동작하며, 모든 복잡한 JavaScript/TypeScript 패턴을 100% 커버하지는 못함
  - runtime 조립되는 URL, 변수 기반 경로 등은 일부 누락될 수 있음

> **교훈 4**  
> 연관관계 도출은 “한 번에 완벽히” 만들 수 있는 기능이 아니며,  
> **Parser → Builder 구조**를 통해 단계적으로 확장해 나가야 유지보수가 가능하다.

## 6. 전역 컨텍스트, INFERRED 제거, 그리고 실패 사례

최근(2025-11-23 기준) 가장 큰 구조적 변경은 다음 두 가지입니다.

1. **전역 파일 컨텍스트 도입 (`util/file_context.py`)**
2. **INFERRED 파일/컴포넌트 자동 생성 로직 전면 제거**

### 6.1 왜 INFERRED 파일이 문제가 되었는가?

- 과거에는 파일 ID/경로를 찾지 못하는 상황에서
  - `inferred/INVENTORY_AUDIT.inferre` 와 같은 **가짜 파일 경로/이름**을 만들어 메타DB에 저장하는 방식으로 “때우는” 로직이 존재
- 문제점
  - 실제로 존재하지 않는 파일이 `files` 테이블에 기록 → 후속 분석 및 정합성 검증이 불가능
  - “어떤 원본 파일에서 나온 쿼리인지”를 추적할 수 없어 **디버깅·검증이 막히는 상황**을 초래
  - 정답지와 비교했을 때, “소스에는 없는 파일명”이 메타DB에 등장하여 혼란 가중

### 6.2 전역 파일 컨텍스트의 개념

자세한 내용은 `docs/11_전역컨텍스트_및_파일출처_관리.md` 참고.

- 각 로딩 단계(XML/Java/프론트엔드 등)에서
  - 파일을 열자마자 **전역 컨텍스트 스택에 `push_file(...)`**
  - DB 기록/컴포넌트/관계 생성 시에는 항상 `require_current_file()` 을 통해
    - `project_id`, `file_id`, `file_path`, `file_type` 을 필수로 확보
  - 처리 종료 시에는 `finally` 블록에서 `pop_file()` 호출
- `require_current_file()` 에 컨텍스트가 없으면
  - **즉시 FATAL ERROR 로 종료**
  - 더 이상 inferred 파일을 만들어서 이어가지 않고, “컨텍스트가 왜 비었는지”를 디버깅하도록 강제

### 6.3 설계 변경 후 실패 사례에서의 교훈

- XML, Java, 프론트엔드 어느 단계에서든
  - 컨텍스트 설정을 빼먹으면 `현재 파일 컨텍스트가 설정되지 않았습니다` 예외로 즉시 중단
  - 이는 “보강”이 아니라, **누락된 버그를 빨리 드러내기 위한 fail-fast 설계**입니다.
- `tables`/`components` 등 주요 엔티티에서도
  - 예전처럼 없는 컴포넌트를 INFERRED 로 만들지 않고,
  - “테이블 컴포넌트 누락”과 같은 런타임 오류를 내도록 변경

> **교훈 5**  
> “조용히 때우는 보강”은 버그를 숨기고,  
> **명시적으로 실패하도록 설계하는 것**이 장기적으로 훨씬 안전하다.

## 7. 테스트와 실패사례에서 얻은 Lessons & Learned

여러 차수의 테스트 결과 보고서(1~6차), 개선계획서 Q&A, 개발불가/개선안 문서들을 통합하면, 다음과 같은 공통 패턴의 교훈을 얻을 수 있습니다.

### 7.1 공통 실패 패턴

1. **새 기능이 기존 기능을 깨뜨림**
   - Enhanced 파서 도입 시, 기존 XML 파싱까지 전부 0건이 되는 사고 발생
   - 교훈: 새 기능은 항상 “토글 가능 + Fallback 보장” 상태로 넣고, 기본 기능이 깨지지 않는지 먼저 확인해야 함.
2. **예외가 조용히 삼켜져서 문제 인지가 늦어짐**
   - include 처리, 동적 SQL 처리 등에서 내부에서 예외를 덮어버려 상위 레이어가 실패를 인지하지 못했던 사례들
   - 교훈: 파이프라인 전체에서 **에러는 가능한 한 위로 전파**하고, 최상단에서 일관된 FATAL 로그를 남기는 구조가 필요.
3. **설계는 야심차지만, 자원/시간 제약을 무시한 계획**
   - 모든 동적 분기를 펼치는 설계, 무한 재귀에 가까운 include 해석 등
   - 교훈: 이론적 완벽함보다는, 목표(누락 없는 대략적 분석)에 맞는 현실적인 범위를 먼저 정해야 한다.

### 7.2 성공 패턴

1. **설정 기반의 제한과 토글**
   - depth/paths/제외 파일 패턴 등을 YAML 로 관리하여, 프로젝트별 특성에 맞춰 조정 가능
2. **Parser/Builder 역할 분리**
   - 파싱(단서 수집)과 관계 구축을 분리함으로써, 어느 단계에서 문제가 생겼는지 추적이 쉬워짐
3. **정답지/보고서 기반의 회귀 테스트**
   - 정답지(백엔드 매핑표)와 메타DB를 비교하는 자동 분석을 통해, 중복·누락·과대계상을 수치화하고 회귀 검증에 활용

> **교훈 6**  
> 이 프로젝트의 품질은 “정답지와의 수치 비교”와 “실제 체인 연결 상태” 두 가지 관점에서 계속 확인해야 한다.  
> 한쪽만 보고 판단하면, 전체 품질을 착각할 수 있다.

## 8. 후임 개발자를 위한 실무 체크리스트

마지막으로, 이 프로젝트를 이어받아 유지보수/개선 작업을 할 때 반드시 점검해야 할 체크리스트를 정리합니다.

### 8.1 새 파서/분석 로직을 추가할 때

- [ ] **전역 파일 컨텍스트**를 먼저 설정하고 해제하는지 (`push_file` / `pop_file`)
- [ ] DB에 기록할 때 항상 `project_id`, `file_id` 를 확보하는지
- [ ] 예외를 “조용히 삼키지” 않고, 상위로 올려 **FATAL 로그**가 찍히게 하는지
- [ ] 새 로직이 실패해도 기본 기능으로 Fallback 가능한지
- [ ] 하드코딩된 경로/프로젝트명/ID 를 넣지 않았는지

### 8.2 SQL 분석 로직을 손댈 때

- [ ] **중복 데이터**가 다시 생기지 않도록 UNIQUE 제약 / INSERT OR IGNORE 패턴을 유지했는지
- [ ] 테이블/컬럼이 누락되지 않는지 정답지/리포트로 검증했는지
- [ ] 동적 SQL/`<include>` 등 고난도 영역은 **제한된 범위 내에서만 개선**하는지
- [ ] 성능·메모리 사용량을 sampleSrc 기준으로 최소 한 번은 측정했는지

### 8.3 프론트엔드·백엔드 연관관계를 수정할 때

- [ ] `frontend_loading.py`, `backend_entry_loading.py`, `relationship_builder.py` 의 역할 분리가 유지되는지
- [ ] API_URL → METHOD 매핑이 깨지지 않았는지 (대표 몇 개 엔드포인트를 실제로 따라가볼 것)
- [ ] 프론트엔드 API 패턴 정규식 수정 시, **기존 케이스가 빠지지 않았는지** 회귀 테스트를 했는지
