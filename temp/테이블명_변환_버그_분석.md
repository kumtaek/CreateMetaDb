**_preprocess_sql() 실행 후:**

**테이블명 추출:**

**결론: 점(.)이 언더스코어(_)로 변환되는 버그는 없습니다!**

## 폐쇄망 환경에서 발생하는 버그의 실제 원인 추정

### 가능성 1: CSV(SCH) 파일 로딩 시 문제

**file_loading.py에서 테이블명 처리:**

```python
# 445번 줄
```

**문제점:**
- CSV 파일에 `NP.SUS_CTR_BAS` 형식으로 저장되어 있으면
- `TABLE_NAME` 컬럼에 `NP.SUS_CTR_BAS`가 그대로 들어옴
- 하지만 `table_owner` 컬럼이 `NP`로 분리되어 있으면
- components에는 `SUS_CTR_BAS`만 저장됨 (스키마 제외)

### 가능성 2: SQL에 실제로 `NP_SUS_CTR_BAS`로 작성되어 있음

**폐쇄망 SQL 작성 관습:**
```sql

-- 폐쇄망 환경 (스키마 접두어를 언더스코어로 사용)
SELECT * FROM NP_SUS_CTR_BAS
```

이 경우 소스코드의 버그가 아니라 **실제 SQL 작성 관습의 차이**입니다.

### 가능성 3: CSV 파일의 TABLE_NAME 컬럼 형식 차이

**sampleSrc (현재):**
```

SUS_CTR_BAS,NP
```

**폐쇄망 환경 (추정):**
```
TABLE_NAME,OWNER
NP.SUS_CTR_BAS,NP
```
또는
```
TABLE_NAME,OWNER
NP_SUS_CTR_BAS,NP
```

## 결론

### 소스코드 버그 여부: **버그 없음**

- 점(.)을 언더스코어(_)로 변환하는 로직은 **전체 소스코드에 존재하지 않음**
- SQL 파서는 점(.)을 올바르게 처리함
- 경로 처리는 백슬래시/슬래시만 변환

### 폐쇄망 버그의 실제 원인 (추정)

1. **CSV 파일 형식 차이**
   - sampleSrc: `TABLE_NAME=SUS_CTR_BAS, OWNER=NP` (분리)
   - 폐쇄망: `TABLE_NAME=NP.SUS_CTR_BAS` 또는 `NP_SUS_CTR_BAS` (통합)

2. **SQL 작성 관습 차이**
   - 폐쇄망에서 실제로 `NP_SUS_CTR_BAS` 형식으로 SQL 작성
   - 스키마 구분자로 언더스코어 사용

3. **components 생성 시 스키마 누락**
   - file_loading.py:517에서 `component_name = table_name` (owner 정보 제외)
   - CSV에 `NP.SUS_CTR_BAS`로 들어오면 components에도 그대로 저장
   - SQL에서 `NP_SUS_CTR_BAS`로 파싱되면 매칭 실패
