## 문제 1: INFERRED 테이블이 고아(관계 없음)로 ERD에 표시되는 원인

### 현상
- INFERRED 테이블(file_type != 'CSV')이 ERD에 표시되지만 다른 테이블과 조인 관계가 없는 고아 테이블로 나타남
- 예시: BRANDS, BRANDS_AUX, BRAND_METRICS, CATEGORIES_, CATEGORY, CATEGORY_STATISTICS 등 20개 발견

### 원인 분석

#### 1) INFERRED 테이블 판단 로직
**위치**: `reports/erd_metadata_service.py:255-298` (`_get_tables_with_relationships` 메서드)

```python
# 257줄: INFERRED 테이블 판단
CASE WHEN f.file_type != 'CSV' THEN 1 ELSE 0 END as is_inferred
```

- CSV 파일에서 로드된 테이블이 아니면 INFERRED로 판단
- XML/JAVA 파일에서 추출된 테이블은 모두 INFERRED로 분류

#### 2) 관계 조회 로직
```sql
-- 261-286줄: 관계가 있는 테이블만 조회
WHERE r.rel_type IN ('JOIN_EXPLICIT', 'JOIN_IMPLICIT')
  AND r.del_yn = 'N'
```

- `relationships` 테이블에서 `JOIN_EXPLICIT` 또는 `JOIN_IMPLICIT` 관계만 조회
- 관계가 없으면 조회되지 않음

#### 3) 실제 데이터 확인
- **INFERRED 후보**: 20개 테이블 (file_type = XML/JAVA)
- **JOIN 관계 있음**: 6개 관계만 발견
  - USERS ↔ BRANDS_AUX
  - PRODUCTS ↔ BRANDS
  - PRODUCTS ↔ INVENTORY
  - ORDERS ↔ PAYMENTS
  - ORDERS ↔ BRAND_METRICS
  - ORDERS ↔ INVENTORY_AUDIT

#### 4) 근본 원인
1. **테이블은 추출되었지만 JOIN 관계가 누락됨**
   - `xml_loading.py`, `java_loading.py`에서 SQL 파싱 시 테이블명만 추출
   - JOIN 조건 파싱 실패하거나 `relationships` 테이블에 INSERT하지 않음

2. **SQL 파싱 실패 케이스**
   - 복잡한 JOIN 구문 (다중 테이블, 서브쿼리, 동적 SQL)
   - 별칭(alias) 처리 실패
   - 조건절에 조인 조건이 있는 경우 (WHERE A.id = B.id)

3. **관계 보강 로직 미흡**
   - `consistency_validator.py`에서 관계 보강하지만 INFERRED 테이블까지 커버하지 못함

### 해결 방안

#### 즉시 개선 가능 (리포트 레벨)
1. **ERD 생성 시 고아 INFERRED 테이블 처리**
   - `erd_report_generator.py`: 고아 INFERRED 테이블을 별도 섹션으로 표시
   - 또는 완전히 제외하는 옵션 추가 (현재 `--include-orphan`은 CSV 고아만 처리)

#### 근본 해결 (파서 레벨)
2. **JOIN 파싱 로직 강화**
   - `xml_loading.py`: MyBatis XML의 복잡한 JOIN 구문 파싱 개선
   - `java_loading.py`: Java StringBuilder SQL의 JOIN 패턴 인식 강화
   - `parser/common_sql_analyzer.py`: WHERE 절의 조인 조건 추출

3. **관계 보강 로직 추가**
   - `consistency_validator.py`: INFERRED 테이블 간 관계 추론 로직 추가
   - 컬럼명 매칭으로 FK 관계 추정 (예: USER_ID 컬럼 기반)

## 문제 2: CSV 테이블이 INFERRED로 잘못 표시되는 원인 (예: NP.SUS_CTR_BAS)

### 현상
- CSV 파일에서 `NP.SUS_CTR_BAS`로 업로드된 테이블이 ERD에서 `NP_SUS_CTR_BAS` (언더스코어)로 INFERRED 테이블로 표시됨

### 원인 분석

#### 1) 테이블 저장 구조 불일치

**tables 테이블**
```
table_name: SUS_CTR_BAS
table_owner: NP
component_id: 123
```

**components 테이블**
```
component_id: 123
component_name: SUS_CTR_BAS (또는 SAMPLE.SUS_CTR_BAS)
file_id: (CSV 파일)
```

- `tables`는 스키마와 테이블명을 **분리** 저장
- `components`는 테이블명만 저장 (스키마 정보 없음)

#### 2) SQL 파싱 시 테이블명 추출 방식

**케이스 1: 점(.)으로 구분**
```sql
SELECT * FROM NP.SUS_CTR_BAS
-- 추출: NP.SUS_CTR_BAS
```

**케이스 2: 언더스코어(_)로 구분**
```sql
SELECT * FROM NP_SUS_CTR_BAS
-- 추출: NP_SUS_CTR_BAS
```

#### 3) 매칭 실패 과정
1. CSV에서 `tables` 테이블에 등록: `table_name=SUS_CTR_BAS, table_owner=NP`
2. `components` 테이블에 등록: `component_name=SUS_CTR_BAS`
3. SQL 파싱 시 `NP_SUS_CTR_BAS` 추출
4. `components`에서 `NP_SUS_CTR_BAS` 검색 → **매칭 실패**
5. 새로운 테이블로 판단하여 `components`에 INSERT (file_type = XML/JAVA)
6. ERD 생성 시 `file_type != 'CSV'`이므로 **INFERRED로 분류**

#### 4) 실제 데이터 확인 결과
- 현재 sampleSrc 프로젝트에서는 `NP.SUS_CTR_BAS` 케이스가 **없음**
- 모든 CSV 테이블이 단일 owner (`SAMPLE`, `SCOTT`)로 일관되게 저장됨
- 하지만 다른 프로젝트에서 발생 가능한 일반적인 문제

### 해결 방안

#### 즉시 개선 가능
1. **테이블명 정규화 함수 추가**
   ```python
   def normalize_table_name(schema, table):
       # NP.SUS_CTR_BAS, NP_SUS_CTR_BAS 모두 동일하게 처리
       if schema:
           return f"{schema}.{table}".upper()
       return table.upper()
   ```

2. **components 생성 시 스키마 포함**
   - `file_loading.py`: CSV 로드 시 `component_name = f"{owner}.{table_name}"`
   - `xml_loading.py`, `java_loading.py`: SQL 파싱 시 스키마 포함

#### 근본 해결
3. **테이블 매칭 로직 개선**
   - `parser/common_sql_analyzer.py`: 테이블명 추출 시 정규화
   - 점(.), 언더스코어(_) 모두 동일하게 처리
   - `tables` 테이블 조회 시 `table_owner.table_name` 형식으로 매칭

4. **중복 테이블 병합**
   - `consistency_validator.py`: 동일 테이블의 다른 형식 감지 및 병합
   - 예: `NP.SUS_CTR_BAS`와 `NP_SUS_CTR_BAS`를 하나로 통합

## 문제 3: 백엔드 매핑 리포트에서 테이블/조인조건 중복 표시

### 현상
- 백엔드 매핑 리포트에서 동일한 테이블, 조인 조건이 중복으로 표시됨

### 원인 분석

#### 1) relationships 테이블의 중복 데이터

**USE_TABLE 관계 중복 (5건 발견)**
```
finalQuery -> USERS_ (2회)
inventoryQuery -> PRODUCTS_ (2회)
query -> USERS (2회)
queryBuilder -> USERS_ (2회)
sql -> USERS (2회)
```

**JOIN 관계 중복 (6건 발견)**
```
PRODUCTS - CATEGORIES (동일 조인 조건 3회)
USERS - ORDERS (동일 조인 조건 3회)
CATEGORIES - PRODUCTS (동일 조인 조건 2회)
ORDER_ITEMS - ORDERS (동일 조인 조건 2회)
PRODUCTS - BRANDS (동일 조인 조건 2회)
USERS - USER_PROFILES (동일 조인 조건 2회)
```

#### 2) UNIQUE INDEX 제약 부족

**현재 INDEX** (`database/create_table_script.sql:179`)
```sql
CREATE UNIQUE INDEX IF NOT EXISTS ix_relationships_01
ON relationships (src_id, dst_id, rel_type);
```

- `join_condition` 컬럼이 UNIQUE INDEX에 **포함되지 않음**
- 동일한 테이블 쌍, 동일한 관계 타입이라도 조인 조건이 다르면 중복 INSERT 가능

#### 3) 리포트 생성 로직의 중복 제거 부족

**backend_mapping_report_generator.py**

**244-278줄: `_load_metadata_use_tables()`**
```python
meta_map.setdefault(key, []).append({
    'owner': table_owner or 'UNKNOWN',
    'table': table_name or ''
})
```
- 동일한 테이블을 리스트에 중복으로 추가
- `set()` 사용하지 않음

**280-391줄: `_load_metadata_join_conditions()`**
```python
# 366-377줄: normalized_conditions = set()으로 중복 제거 시도
normalized_conditions = set()
for cond in conditions:
    if '=' in cond:
        parts = [p.strip() for p in cond.split('=', 1)]
        if len(parts) == 2:
            left_part, right_part = parts
            if left_part.endswith('.') or right_part.endswith('.'):
                continue  # 컬럼 없는 조건 필터링
            norm_cond = ' = '.join(sorted(parts))
            normalized_conditions.add(norm_cond)
```
- 조인 조건은 정규화하여 중복 제거
- 하지만 `relationships` 테이블에 이미 중복 데이터가 있어 효과 제한적

#### 4) 중복 발생 원인

1. **XML 파싱 시 중복 INSERT**
   - `xml_loading.py`: 동일한 테이블을 여러 번 참조하는 SQL에서 중복 INSERT
   - 예: `SELECT * FROM USERS u1 JOIN USERS u2` → USERS를 2번 INSERT

2. **Java 파싱 시 중복 INSERT**
   - `java_loading.py`: StringBuilder로 동적 생성된 SQL에서 중복 파싱

3. **관계 보강 시 중복**
   - `consistency_validator.py`: 기존 관계 확인 없이 추가 INSERT

### 해결 방안

#### 즉시 개선 가능 (리포트 레벨)
1. **리포트 생성 시 중복 제거**
   ```python
   # _load_metadata_use_tables() 수정
   def _load_metadata_use_tables(self):
       meta_map = {}
       # ...
       for comp_name, table_name, table_owner in cursor.fetchall():
           key = (comp_name or '').upper()
           table_key = (table_owner, table_name)
           if key not in meta_map:
               meta_map[key] = set()
           meta_map[key].add(table_key)  # set 사용
       # 리스트로 변환
       return {k: [{'owner': t[0], 'table': t[1]} for t in v]
               for k, v in meta_map.items()}
   ```

2. **_format_tables() 수정**
   ```python
   def _format_tables(self, tables):
       seen = set()
       formatted = []
       for tbl in tables:
           owner = tbl.get('owner', 'UNKNOWN')
           name = tbl.get('table', '')
           key = f"{owner}.{name}"
           if key not in seen:
               seen.add(key)
               formatted.append(key if owner != 'UNKNOWN' else name)
       return formatted
   ```

#### 근본 해결 (데이터 레벨)
3. **relationships INSERT 전 중복 체크**
   ```python
   # xml_loading.py, java_loading.py 공통
   def insert_relationship(src_id, dst_id, rel_type, join_condition):
       # 기존 관계 확인
       existing = db_utils.execute_query(
           "SELECT relationship_id FROM relationships "
           "WHERE src_id=? AND dst_id=? AND rel_type=? "
           "AND (join_condition=? OR (join_condition IS NULL AND ? IS NULL))",
           (src_id, dst_id, rel_type, join_condition, join_condition)
       )
       if existing:
           return  # 이미 존재하면 INSERT 안함
       # INSERT
   ```

4. **UNIQUE INDEX 수정 (주의: DDL 변경 금지 원칙 위배)**
   - 현재 원칙상 `database/create_table_script.sql` 수정 금지
   - 대안: 애플리케이션 레벨에서 중복 체크 철저히

## 종합 결론

### 공통 원인
1. **SQL 파싱의 한계**
   - 복잡한 SQL 구문 파싱 실패
   - 동적 SQL, 별칭 처리 미흡

2. **테이블명 정규화 부족**
   - 스키마.테이블 vs 스키마_테이블
   - 대소문자 혼용

3. **데이터 중복 허용**
   - UNIQUE 제약 부족
   - INSERT 전 중복 체크 없음

### 우선순위별 개선 방안

#### 우선순위 1 (즉시 가능 - 리포트 레벨)
- 백엔드 매핑 리포트 중복 제거 로직 추가
- ERD 고아 INFERRED 테이블 처리 옵션

#### 우선순위 2 (단기 - 애플리케이션 레벨)
- relationships INSERT 전 중복 체크
- 테이블명 정규화 함수 추가
- components 생성 시 스키마 포함

#### 우선순위 3 (장기 - 파서 레벨)
- SQL 파싱 로직 전면 개선
- JOIN 조건 추출 강화
- 관계 보강 로직 추가

### 영향도 분석
- **문제 1**: ERD 정확성 저하 (고아 테이블로 오인)
