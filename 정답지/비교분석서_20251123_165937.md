### 2.2 메타DB 추가 인식(MyBatis) – 정답지 스코프 밖

- 메타DB는 추가로 다음 경로의 XML도 분석함:

    - `findUsersWithAliasOmission`
    - `findUsersWithAnsiJoin`
    - `findUsersWithInferredBrand`
    - `findUsersWithMixedJoins`
    - `findUsersWithScatteredConditions`

#### 원인 분석

- `src/com/example/dynamicquery/UserMapper.xml`은 **JOIN/별칭/INFERRED 컬럼 테스트용 MyBatis 샘플**이며, 정답지에는 포함되어 있지 않음.
- 메타DB는 `XmlParser + XmlLoadingEngine`를 통해 **모든 MyBatis XML을 공평하게 처리**하므로, 위와 같은 테스트용 쿼리도 정상적으로 `SQL_SELECT` 컴포넌트로 등록됨.

#### 평가 및 개선 방향

- 메타DB 입장: **추가 9건 인식은 바람직한 확장**이며, “누락 없는 대략적 분석” 목표에 부합.
- 정답지 입장: 본래 “주요 비즈니스 Mapper”만을 비교 대상으로 삼았기 때문에 dynamicquery 샘플은 의도적으로 제외된 상태.
- 제안
  - 정답지를 “검증 스코프 문서”로 간주하고, MyBatis 섹션에 **비고 컬럼**을 추가하여  
    - `src/main/resources/mybatis/mapper` = 핵심 비즈니스 Mapper  
    - `src/com/example/dynamicquery` = JOIN/INFERRED 검증용 샘플  
    로 구분해 두면, 후임이 헷갈리지 않음.
  - 코드(파서)는 현재 동작이 적절하므로 **추가 수정 불필요**.

  - 별도 섹션으로 “테스트/성능/서비스 SQL(정답지 스코프 외)” 목록을 요약해서,

  - 정답지에 정의된 MyBatis/JPA/DAO 쿼리 184건은 모두 메타DB에 존재.
  - SQL_Type, Path, File, Query ID 기준으로 조회 시, 각 행마다 최소 1개의 SQL 컴포넌트가 매칭됨.

     - 역할: JOIN/별칭/INFERRED 패턴 검증용 샘플
     - 판정: **정답지 스코프 밖, 메타DB 정상 동작**
  2. JPA 테스트/INFERRED 샘플
     - `JoinQueryRepository.java` 의 9개 @Query
     - `OrderRepository.findOrdersWithInferredBrandMetric` 1개 (INFERRED 테이블 조인 샘플)
     - 판정: **정답지 스코프 밖(테스트/검증용), 메타DB 정상 동작**
  3. Java 문자열 기반 테스트/성능/서비스 SQL
     - performance/testcase/service/model 패키지의 125개 SQL
     - 판정: **정답지 스코프 밖(테스트·성능·서비스 계층), 메타DB 정상 동작**

> 요약: 이번 차이는 **정답지 문제(스코프 정의)**에 가깝고,

## 6. 최적 개선안 제안 (누락 없는 대략적 분석 관점)

마지막으로, `docs/기능개선/기능개선_종합개선이력_20251123.md` 와 기존 비교문서를 참고한 뒤,  
“정확·정교한 파싱이 아니라 **누락 없는 대략적 분석**”이라는 목표에 맞춘 개선안을 정리합니다.

### 6.1 정답지 활용 방식 개선

1. **정답지를 “검증 스코프 정의서”로 명확히 위치시킬 것**
   - MyBatis: `src/main/resources/mybatis/mapper` 만을 “백엔드 핵심 Mapper”로 본다는 점을 문서에 명시
   - JPA: `src/main/java/com/example/jpa/repository` 만 정답지 스코프, `JoinQueryRepository` 등은 “샘플/테스트 레이어”로 분리
   - Java 문자열: DAO 3개만 백엔드 매핑 스코프, 나머지는 “파서 테스트/성능용”으로 분리

2. **정답지에 “스코프 외 추가 인식” 요약 섹션을 추가**
   - 각 구간별로 “메타DB가 추가로 인식하는 쿼리 목록/건수”를 요약해 두면,
   - 향후 비교 시 “왜 메타DB 건수가 더 많은지”를 바로 이해할 수 있음.

### 6.2 메타DB 측 개선안 (소스 수정 없이 정책 차원)

1. **검증 스크립트 표준화(현재 우리가 수행한 방식)**  
   - 정답지 테이블을 파싱해 `metadata.db` 를 조회하는 **간단한 비교 스크립트**를  
     - `tools/compare_with_answer_key.py` 또는 별도 temp 스크립트로 정리해 두고,  
     - 회귀 테스트 시 “정답지 184건이 모두 존재하는지”만 자동 체크하도록 하는 것이 좋음.
   - 이때, 추가 인식된 쿼리는 실패로 보지 말고 **정보성 로그**로만 보고.

2. **리포트/통계에서 스코프 필터 제공**
   - 리포트나 통계에서
     - “정답지 스코프(핵심 비즈니스)”
     - “테스트/성능/샘플 코드”  
     를 구분할 수 있는 필터(예: 파일 경로 prefix 기반)를 제공하면,
   - 운영용 리포트에서는 핵심 경로만 보고, 분석/테스트 시에는 전체를 볼 수 있음.

3. **INFERRED 샘플에 대한 별도 태깅**
   - `OrderRepository.findOrdersWithInferredBrandMetric`, dynamicquery XML 등은
     - “INFERRED 기능 검증용 샘플”이라는 점을 메타DB나 리포트에서 태그(코멘트)로 남겨두면,
     - 후임이 이 쿼리들을 보고 “실제 테이블이 누락된 것인지, 의도된 샘플인지”를 쉽게 판단할 수 있음.

### 6.3 결론

- 현재 구현된 분석 파이프라인은 **정답지에 정의된 백엔드 매핑을 100% 커버**하고 있으며,
  - 추가로 테스트/성능/샘플 코드까지 폭넓게 인식하고 있습니다.
- 따라서, “정확하고 정교한 파싱”보다는 “누락 없는 대략적 분석”을 목표로 하는 현 프로젝트 철학에 **충분히 부합**합니다.
- 앞으로의 개선 포인트는 **파싱 로직 자체를 더 복잡하게 만드는 것**이 아니라,
  - 정답지 스코프 정의,
  - INFERRED 샘플 태깅,
  - 리포트/검증 도구의 필터링/요약 기능을 강화하는 방향이 **최적의 개선안**입니다.
